# 规范用语

> 规范性。RFC-0024「规范用语」。2026-11-24 新增（ADR-0276）：只定义这些词的约束力，不改已有正文的任何措辞。

规范正文用下面五组词表达一条规则有多强的约束力，含义与 RFC 2119 / RFC 8174 的关键词相同。同一组里的几种写法约束力相同，正文按行文选用。

| 用语 | 同组的写法 | 约束力 | RFC 2119 |
| --- | --- | --- | --- |
| 必须 | 须 | 绝对的要求。不照做就不符合规范 | MUST |
| 不得 | 不能、不可、禁止 | 绝对的禁止。这样做就不符合规范 | MUST NOT |
| 应当 | 应、应该 | 推荐的做法。有站得住的理由可以不照做，但要先弄清楚后果；不照做仍然符合规范 | SHOULD |
| 不应当 | 不应、不应该 | 不推荐的做法。有站得住的理由可以这样做，同上 | SHOULD NOT |
| 可以 | 可、可选 | 任选。做与不做都符合规范；一方做了、另一方没做，两边仍然要能互通 | MAY |

## 读法

1. **陈述句也是要求。** 正文里的规则大多直接写成陈述句，不逐句加「必须」：「宿主把握手声明的操作登记为代理操作」「读不出就当作没有」「错误码都是 `KERNEL_CAPABILITY_006`」。规范性内容里描述实现的行为、线上的格式或取值的陈述句，约束力与「必须」相同；「只能」「一律」「总是」「只认」这类写法是在强调它，不是另一个等级。
2. **只在规范性内容里有约束力。** 规范性内容是已采纳的 RFC 的正文、`conventions/`、`manifest/`、`plugin/`、`protocol/`、`packaging/`、`provider/`、`migration/` 的文本，以及一致性向量与档表。下面这些只是说明，里面出现的「必须」「应当」不构成要求：RFC 的「动机」「备选方案」「非目标与未决」；示例；修订注记里记来历的话（「以前…」）；`README`、`CHANGELOG.md` 与 ADR（RFC-0024「规范与决策记录」）。
3. **要求落在行为上，不落在名字上。** 正文里的 .NET 类型名、方法名与选项名是参考实现落实这条规则的地方，别的语言不必同名；它们所描述的行为仍然是要求。
4. **只约束认领了所属档的实现。** 一条要求属于它所在文件的一致性档（RFC-0024「一致性档」），实现只对自己认领的档负责。`experimental` 档里的要求同样是要求，只是这个档不计入成熟度的判定。
5. **按意思读，不按字面搜。** 这几个词在叙述事实时没有约束力：「存储不能同时表达两者」里的「不能」说的是做不到，「可选依赖」「可选成员」里的「可选」是名词的一部分。拿不准一句话是要求还是叙述时，以它是否描述了对端或使用者观察得到的行为为准；仍然拿不准的，是正文的缺陷，按修订流程写明（RFC-0024「版本」第 3 条的 MINOR）。

## 新写的正文

新增与修订的规范性句子从上表选词：要求用「必须」或直接写成陈述句，禁止用「不得」，建议用「应当」，任选用「可以」。不用「尽量」「原则上」「一般」这类说不清约束力的词；一条规则有例外时把例外写出来。
