# XiHan Spec 测试审查

对每个测试给出「保留、改写、合并或删除」结论，并指出它保护的规范条文或门禁。

- 保留：规范或向量出错时会失败，覆盖文法、判定、错误码与消息键、档表覆盖、运行器对违规插件的识别。
- 改写：把期望值硬编码在测试里而不是读向量；只断言函数被调用；依赖 map 遍历顺序或固定 sleep；没有失败路径。
- 合并：与相邻用例输入和断言等价，不能提供额外定位。
- 删除：不可能失败，或已被同层更清晰的测试完整覆盖。

## 规范仓库专项

- 规则测试从 `conformance.Vectors` 读向量回放，规则与向量互相验证；新增向量文件后要有对应的回放。
- 档表测试核对每个向量文件至少属于一档；`tools/speccheck` 核对规范文件、RFC 状态行、错误码与清单 Schema，测试先确认找到的是真正的仓库根，避免在别处跑出空结果却通过。
- 运行器的每个用例都要有两面证据：合规的假插件通过，`legacy` 假插件在它针对的规则上失败。
- 涉及平台差异（命名管道、Unix 套接字、`.exe`）的测试注明只在哪个平台有效，不能在 CI 的 Linux 上静默跳过 Windows 路径而不说明。
- 时间相关的用例用截止时间与上下文，不用长时间真实等待。

输出按风险排序并附文件和行号。除非用户要求运行，否则先静态审查；不得通过删除测试、删除向量用例或放宽 CI 来解决问题。
