## 摘要

AI 子系统以 `Microsoft.Extensions.AI` 的 `IChatClient` / `IEmbeddingGenerator` / `AITool` 为线格式，不另造模型接口：框架提供按名字解析模型 Provider 的目录、带提示词 / 护栏 / 工具的聊天入口、把 `[Operation]` 契约桥接成模型可调用工具的目录，以及"切块 → 嵌入 → 向量存取 → 检索 → 提示增强"的知识库流水线。模型端点与向量存储都是外部资源，由 Provider 包适配；进程内的工具目录零外部依赖。能力 `ai.chat@1`、`ai.embedding@1`、`ai.tools@1`、`ai.knowledge@1`。

| 能力 | 含义 | 默认实现 |
| --- | --- | --- |
| `ai.chat@1` | 按名字解析 `IChatClient`；`IAIChat` 在其上叠加提示词、护栏与工具 | 无（`AI.OpenAI` 适配 OpenAI 兼容端点） |
| `ai.embedding@1` | 按名字解析 `IEmbeddingGenerator<string, Embedding<float>>` | 无（`AI.OpenAI`） |
| `ai.tools@1` | 工具目录：显式登记的 `AITool` 与 `Expose.Ai` 的操作契约桥接成的 `AIFunction` | `AI.Abstractions` 的 `AIToolsFeature`（进程内，`role: default`） |

## Provider 目录

- 配置节 `XiHan:AI`：`DefaultProvider`、`DefaultEmbeddingProvider`（框架自带目录的默认名，见下文「默认名」），`Providers:<name>` 下 `Kind`（Provider 种类，必填，没有缺省；由工厂的 `Kind` 匹配，如 `openai`）、`Endpoint`（绝对的 http 或 https 地址；不写或空串表示 Provider 的官方端点）、`ApiKey`、`ChatModel`、`EmbeddingModel`、`EmbeddingDimensions`（≥ 1 的整数）、`TimeoutSeconds`（正数，默认 100；怎样计时与归因见「超时与取消」）、`Properties:<key>`（透传给工厂的字符串字典）。名字文法 `^[a-z0-9][a-z0-9._-]{0,63}$`。
- 读取配置时值不合法即抛出 `ArgumentException`、启动失败，不按缺省处理：Provider 缺 `Kind`；`Endpoint` 不是绝对的 http(s) 地址（写错的端点不能退回官方端点、把 `ApiKey` 发给它）；`EmbeddingDimensions`、知识库的 `Dimensions` / `ChunkSize` / `Top` 不是 ≥ 1 的整数，`ChunkOverlap` 不是 ≥ 0 的整数；`TimeoutSeconds` 不是有限的正数；护栏的 `Enabled` / `UseBuiltInInjectionHeuristics` 不是 `true` / `false`；提示词缺 `Template`；名字不合文法。
- `IAIProviderCatalog`：`Providers`、`DefaultProvider`、`DefaultEmbeddingProvider`、`Find(name)`、`ResolveChatClient(name?)`、`ResolveEmbeddingGenerator(name?)`、`Invalidate(name?)`。解析结果按名字缓存，`Invalidate` 释放缓存实例（下次解析重建），`name` 为空时清全部。`AIOptions` 在装配时从配置读一次、登记为单例，重建用的仍是这份选项：`Invalidate` 不会拾取 `XiHan:AI:Providers` 的配置变化，改了 Provider 配置要重启应用；它用于丢弃坏掉的客户端（如连接状态异常）后重建。框架不监听配置变化。
- 默认名（2026-11-04，ADR-0110）：`DefaultProvider` / `DefaultEmbeddingProvider` 是目录此刻的默认聊天 / 嵌入 Provider 名，`null` 表示没有默认。`ResolveChatClient(null)` / `ResolveEmbeddingGenerator(null)` 按它们解析；`IAIChat` 与知识库流水线在请求没写 Provider 时也只问目录的这两个成员，不读 `XiHan:AI` 配置——应用以自己的目录（如落库的目录）替换框架的实现后，默认名随目录走。
  - 框架自带的目录从配置给出：`DefaultProvider` 是配置的 `DefaultProvider`，没写且只配了一个 Provider 时是它，否则没有；`DefaultEmbeddingProvider` 是配置的 `DefaultEmbeddingProvider`，没写时同 `DefaultProvider`。
  - 两个成员是同步的只读属性、不带取消令牌：目录的读取本来都是同步的（`Find`、`Resolve*`），要查库的目录持内存快照、写入后重载，默认名是快照的一部分，读它不做 I/O。
  - 聊天与嵌入的默认可以相同也可以不同；目录只支持一个默认时两者相同。默认名不保证在 `Providers` 里（例如配置写错），按它解析时与其他未配置的名字一样报 `AI_NOTFOUND_001`（`ai.provider.not_found`）。
- 名字未配置 → `AI_NOTFOUND_001`；没给名字而目录没有默认 → `AI_NOTFOUND_001`，消息键聊天 `ai.provider.default_missing`、嵌入 `ai.provider.embedding_default_missing`（不带参数；目录的 `Resolve*(null)` 与 `IAIChat`、知识库流水线同用这两个键）；`Kind` 没有登记对应的 `IChatClientFactory` / `IEmbeddingGeneratorFactory` → `AI_NOTFOUND_001`；缺 `ChatModel` / `EmbeddingModel` 等必填项 → `AI_VALIDATION_001`。
- Provider 包实现 `IChatClientFactory { Kind; Create(AIProviderOptions) }` 与 `IEmbeddingGeneratorFactory`，以 `AddAIChatClientFactory<T>()` / `AddAIEmbeddingGeneratorFactory<T>()` 登记；同一 `Kind` 登记两次以后者为准。

## 聊天

- `IAIChat`（作用域服务）：`CompleteAsync(AIChatRequest) → Result<ChatResponse>`、`StreamAsync(AIChatRequest) → Result<IAsyncEnumerable<ChatResponseUpdate>>`（校验、提示词与护栏在返回流之前完成；流开始后的错误在枚举时抛出，超时是 `TimeoutException`，见「超时与取消」）。
- `AIChatRequest`：`Messages`、`Provider`、`Prompt`（提示词名）与 `PromptArguments`、`Tools`（工具名列表，空表示不带工具）、`Options`（`ChatOptions`，`Tools` 会被目录绑定结果覆盖）、`SkipGuardrails`（默认 false）。
- 顺序：提示词渲染（不存在 → `AI_NOTFOUND_002`，参数缺失 → `AI_VALIDATION_001`）作为首条 `System` 消息 → 工具绑定（名字不存在 → `AI_NOTFOUND_003`）→ 护栏按登记顺序检查全部 `User` 消息（任一 `Block` → `AI_DENIED_001`，`details.guardrail` / `details.reason`；护栏抛异常 → `AI_UNEXPECTED_001`）→ 解析 Provider（请求没写 `Provider` 时取目录的 `DefaultProvider`，没有即 `AI_NOTFOUND_001`、`ai.provider.default_missing`）→ 调用。模型端点返回错误或不可达 → `AI_UNAVAILABLE_001`，超时 → `AI_TIMEOUT_001`，调用方取消 → 抛出 `OperationCanceledException`（归因见「超时与取消」）。
- 护栏：`IAIGuardrail { Name; InspectAsync(messages) → Result<GuardrailVerdict> }`，`GuardrailVerdict.Allow()` / `Block(reasonKey, reasonArguments?)`（原因是消息键加参数，按调用方区域翻译后放进 `details.reason`）；`AddAIGuardrail<T>()` 登记。内置 `KeywordBlocklistGuardrail`（`XiHan:AI:Guardrails:Enabled` 为 true 时登记）：`BlockedKeywords`（不区分大小写的子串）、`InjectionPatterns`（正则）、`UseBuiltInInjectionHeuristics`（默认 true，内置中英文提示注入模式）。直接从目录解析 `IChatClient` 的调用不经护栏。
- 提示词：`AIPromptTemplate(Name, Template, Description?)`，占位符 `{name}`，`{{` / `}}` 转义成字面量；`Render(arguments) → Result<string>`。`IAIPromptCatalog { Find(name); All() }` 合并 `AddAIPrompt(template)` 的显式登记（优先）与配置 `XiHan:AI:Prompts:<name>:Template` / `:Description`。名字文法同 Provider。

## 工具

- `Expose` 新增 `Ai = 16`，`All` 含之；插件握手的 `expose` 接受 `ai`。
- `IAIToolCatalog { All(); Find(name); Bind(InvocationContext caller) }`：`All` / `Find` 返回声明（`AIFunctionFactory.CreateDeclaration`：名字、描述、输入 / 输出 Schema）；`Bind` 返回绑定到调用方上下文的可执行工具。来源：`AddAITool(AITool)` 显式登记的工具原样返回；登记表里 `Expose` 含 `Ai` 且非 `Stability.Internal` 的操作各成一个 `AIFunction`。
- 操作工具名默认 `<resource>_<verb>`（`-` 与 `.` 换 `_`；超过 64 个字符时截成前 55 个字符 + `_` + 全名 SHA-256 的前 8 位十六进制，任何操作 ID 都推得出合法且稳定的名字），`XiHan:AI:Tools:<操作 ID>` 覆盖；名字不合法或重复在构建目录时以 `AI_VALIDATION_001` 启动失败（重复的消息键 `ai.tool.duplicate`，带出撞名的两方）。工具目录在启动时构建：`AIToolsFeature` 与 `OpenAIFeature` 的 `StartAsync` 都解析 `IAIToolCatalog`，只装其中任何一个（聊天要用工具目录），工具名问题都在启动时失败，不推迟到第一次聊天（后者见 ADR-0086）。描述取消息目录里 `<操作 ID>.description`（ID 里的 `-` 换 `_`）按调用方区域翻译，没有则为空。输入 Schema 取 `OperationSchema.Request`，没有时 `{"type":"object"}`；输出 Schema 取 `Response`。
- 调用：参数序列化成请求 JSON（某个参数序列化不了 → 不调用操作，以 `AI_VALIDATION_001`、消息键 `ai.tool.argument_invalid` 交给模型），在新作用域、新 `InvocationContext` 里经完整管道执行，取消令牌是驱动它的聊天调用交给 Provider 的令牌（经 `IAIChat` 时是调用方的取消与 Provider 超时链接而成，见「超时与取消」；直接调用 `AIFunction` 时是传入的令牌）。新上下文复制调用方的 trace-id、Baggage、截止时间与安全上下文（主体与租户，在工具被调用时读取），工具以调用方身份执行：不复制凭据，Authenticate 阶段没有凭据可认证，保留复制来的主体；Authorize 阶段以该主体按契约判定（声明了 `Permission` 的操作，调用方有权限才放行），工具不能绕过授权，也不会因丢失身份被一律拒绝。成功返回响应 JSON，失败返回 `{"error":"<码>","message":"<按调用方区域翻译的文案>"}`——错误交给模型处理，不抛异常。

## 知识库

- 模型：`KnowledgeIngestRequest(DocumentId, Text, Collection?, Metadata?, Provider?, Chunking?)`、`KnowledgeRecord(Id, DocumentId, ChunkIndex, Text, Metadata, Vector)`、`RetrievedChunk(Record 去掉向量 + Score)`、`RetrievalFilter(DocumentIds?, Metadata?)`（元数据按键值相等过滤）、`KnowledgeQuery(Text, Collection?, Top, Filter?, Provider?, MinScore?)`、`ChunkingOptions(MaxChunkSize, Overlap)`。记录 ID 为 `<documentId>#<chunkIndex>`。
- `IChunkingStrategy.Chunk(text, options)`；内置 `FixedWindowChunkingStrategy`：按字符的固定窗口，`Overlap` 裁到 `[0, MaxChunkSize − 1]`，换行统一为 `\n`，空白块丢弃。
- `IKnowledgeStore`（Provider 契约）：`UpsertAsync(collection, records[])`、`DeleteAsync(collection, documentIds[])`、`TrimAsync(collection, documentId, chunkCount)`（删除该文档块序号 ≥ `chunkCount` 的记录，块序号更小的不动）、`SearchAsync(collection, vector, top, filter?) → Result<IReadOnlyList<RetrievedChunk>>`（按 Score 降序）。集合不存在：写入时创建，搜索返回空，删除与裁剪视为成功。
- `IKnowledgeIngestor.IngestAsync(requests[]) → IReadOnlyList<Result<int>>`（每篇文档的块数）、`RemoveAsync(collection, documentIds[])`。同一文档重新摄入先写后删：新块全部嵌入、校验维度并写入成功后，才以 `TrimAsync(documentId, 新块数)` 删掉旧版本多出来的块——同 ID 的块由写入覆盖；嵌入、维度校验或写入失败时不删任何旧块，旧文档照常可检索（写入中途失败最多留下新旧混合的块，重试摄入即恢复一致）；裁剪失败返回该错误，新块已在、多余的旧块留待重试摄入删除。新文本切不出块时整篇删除（`DeleteAsync`），返回 0；`IKnowledgeRetriever.RetrieveAsync(query)`；`IRagPromptAugmenter.Augment(question, chunks) → string`（没有块时原样返回问题；配置了 `XiHan:AI:Knowledge:PromptName` 就用它指向的提示词模板，占位符 `{context}` / `{question}`，没配置用内置英文模板）。配置引用的模板在启动时校验（ADR-0074）：增强器创建时从提示词目录取模板，并用代表性的 `{context}` / `{question}` 试渲染一次；模板不存在 → `AI_NOTFOUND_002`，引用了这两个以外的占位符、渲染失败 → `AI_VALIDATION_001`，都以 `FrameworkException` 抛出，不退回内置模板。正式包的 AI 特性都在启动时解析增强器（`AIToolsFeature`、`VectorDataKnowledgeFeature` 与 `OpenAIFeature` 的 `StartAsync`，后者见 ADR-0083），只装其中任何一个，配置错误都在启动时失败；一致性包里只供测试的 `HashingEmbeddingFeature` 不带启动钩子，在第一次解析增强器时抛出。校验之后增强只用创建时取到的模板、只提供这两个参数，没有运行时失败的来源，所以返回 `string`。
- 选项 `XiHan:AI:Knowledge`：`Collection`（默认 `knowledge`）、`Dimensions`（默认 1536）、`ChunkSize`（1000）、`ChunkOverlap`（100）、`Top`（5）、`EmbeddingProvider`、`PromptName`。摄入与检索的嵌入 Provider 取请求的 `Provider`、`EmbeddingProvider`、目录的 `DefaultEmbeddingProvider` 中第一个非空的，都为空即 `AI_NOTFOUND_001`（`ai.provider.embedding_default_missing`）。嵌入维度与 `Dimensions` 不一致 → `AI_VALIDATION_002`；没有 `ai.knowledge` Provider 时调用摄入 / 检索 → `AI_UNAVAILABLE_002`；Provider 不可达（含向量库自身的容量限制）同样是 `AI_UNAVAILABLE_002`，框架自己的知识库没有容量上限，不设单独的"容量已满"文案。摄入与检索的嵌入调用不可达 → `AI_UNAVAILABLE_001`，超时 → `AI_TIMEOUT_001`，调用方取消 → 抛出 `OperationCanceledException`（见「超时与取消」）。

## 超时与取消

Provider 的 `TimeoutSeconds` 由框架落成令牌、按令牌归因（2026-11-02，ADR-0095）：

- 超时令牌：`IAIChat` 与知识库流水线调用 Provider 时，把该 Provider 的 `TimeoutSeconds` 按容器的 `TimeProvider` 落成定时取消，与调用方的取消令牌链接后交给 Provider。时限的范围：
  - 完整应答（`CompleteAsync`）：从调用 Provider 起到它返回，含 Provider 自己的函数调用循环与其中的工具调用。
  - 嵌入：摄入与检索的每一次嵌入批调用。
  - 流式（`StreamAsync`）：等每个更新（含第一个）的时限。只在等 Provider 时计时，调用方处理更新的时间不算，流的总时长不限；计时从开始枚举算起。已定（2026-11-02，ADR-0097）：保留按每次更新计时，不改成整条流的总时限，也不退回不计时——总时限会把长回答、调用方处理得慢的流在正常输出时截断；不计时则卡住的连接没有上限，流里的超时也没有归因。要限制一次对话的总时长，由调用方给自己的取消令牌或调用的截止时间。
  - 直接从目录解析的客户端与生成器不经这一层，没有框架的计时，拿到的是 Provider 的原始行为。Provider 自己的传输超时照常执行（OpenAI 的 `NetworkTimeout` 同取 `TimeoutSeconds`，作用于每次网络请求）。
- 归因只看令牌，Provider 抛出与写成结果同一规则（与 RFC-0004 `DeadlineMiddleware` 同一形状）：
  1. 超时令牌已触发即超时，不论调用方令牌是否也已触发。Provider 抛出的取消不论报的是哪个令牌（两个都触发时 OpenAI SDK 报调用方的那个），Provider 接住取消、正常返回的结果（可能是截断的应答、条数不全的嵌入、提前结束的流）也一样，都按超时报告。
  2. 超时令牌没有触发、调用方令牌已触发即取消：Provider 抛出的取消原样抛出；正常返回的结果不交给调用方，改为抛出调用方的 `OperationCanceledException`。经管道的调用由 `DeadlineMiddleware` 按调用的截止令牌归因（RFC-0004）。
  3. 两个令牌都没有触发：Provider 抛出的取消视为它自己的传输超时，按超时报告；`TimeoutException` 在任何情况下都按超时报告；其他异常是 `AI_UNAVAILABLE_001`；结果原样返回。
- 怎样报告：完整应答与嵌入（摄入、检索）返回 `AI_TIMEOUT_001`（`details.provider` 是 Provider 名，没有显式指定时是目录给出的默认名）；流已交给调用方、不能再返回结果，超时在枚举时抛出 `TimeoutException`（`InnerException` 是 Provider 抛出的异常，写成结果时为空），调用方取消抛出 `OperationCanceledException`，其余传输错误原样抛出。
- 行为变化（2026-11-02）：以前超时只由 Provider 自己执行，框架只按「调用方令牌没有触发的取消即超时」推断。两个同时触发时原样抛出调用方的取消，截止时间没到即 `KERNEL_CANCELLED_001`；Provider 接住取消、返回的截断结果当作成功；流里不做归因，超时以 Provider 自己的取消异常抛出。现在同时触发报 `AI_TIMEOUT_001`，写成结果的同样按令牌归因，流里的超时是 `TimeoutException`。完整应答的时限覆盖 Provider 的整个函数调用循环（以前 OpenAI 只限每次网络请求），工具调用多、总时长可能超过 `TimeoutSeconds` 的应用要调大它。

## 默认实现与 Provider

- `AI.Abstractions`：`AIToolsFeature`（`xihan.ai.tools`，提供 `ai.tools@1`）与所有 AI 特性共用的 `AddAI(configuration)`（幂等）：选项、Provider 目录、`IAIChat`、提示词目录、工具目录、知识库流水线、消息目录。
- `AI.OpenAI`：`OpenAIFeature`（`xihan.ai.openai`，提供 `ai.chat@1` 与 `ai.embedding@1`）登记 `Kind = openai` 的两个工厂：`OpenAIClient`（`Endpoint` 为空时官方端点；`ApiKey` 为空时占位凭据，供本地兼容端点）→ `AsIChatClient()` → `UseFunctionInvocation()`，工具调用在客户端循环里自动执行；网络超时取 `TimeoutSeconds`（`NetworkTimeout`）。容器里有 `IHttpClientFactory` 时经名为 `xihan.ai.openai` 的客户端发请求（应用没有专门配置这个名字时是工厂的缺省客户端，`ConfigureHttpClientDefaults` 的配置同样作用于它），该客户端自身的 `Timeout` 置为不限，超时只以 `TimeoutSeconds` 为准，不被 `HttpClient` 缺省的 100 秒截断；没有工厂时走 SDK 自己的传输。装配与启动不触网；启动时构建工具目录（工具名不合法或重复即失败，上文「工具」）并解析提示增强器，校验知识库配置引用的提示词（上文「知识库」）。
- `AI.VectorData`：`VectorDataKnowledgeFeature`（`xihan.ai.vectordata`，提供 `ai.knowledge@1`，要求 `ai.embedding@1`）把 `IKnowledgeStore` 映射到应用注册的 `VectorStore`：集合定义按 `Dimensions` 构造，余弦距离，`DocumentId` 与 `ChunkIndex` 是可过滤字段；删除与裁剪以过滤条件分页取键再按键删；`DocumentIds` 过滤下推，元数据过滤在取回 `top × 4` 条后在进程内完成；启动时容器里没有 `VectorStore` → `AI_UNAVAILABLE_002` 启动失败。
  - 记录形状（2026-11-04，ADR-0111）：向量键是 `Guid`，由记录 ID（`<documentId>#<chunkIndex>`）确定性推出：记录 ID 的 UTF-8 字节做 SHA-256，取前 16 字节，按 RFC 9562 写上版本 8 与变体位（第 7 字节高 4 位 `1000`、第 9 字节高 2 位 `10`），按大端读成 UUID，如 `cats#0` → `bf5265ac-88dd-8c19-aed4-85f49dee74bb`。同一个记录 ID 永远得到同一个键，重写入覆盖旧记录；记录 ID 原样存在 `RecordId` 字段，`KnowledgeRecord.Id` 与 `RetrievedChunk.Id` 不变。这个算法是存储格式的一部分，改动要重建集合；键形状变化之前建的集合也要重建。连接器不接受 `Guid` 键时，写入与搜索返回 `AI_UNAVAILABLE_002`。
  - 健康项 `ai.vectordata.store`（2026-11-04，ADR-0110，ADR-0030 的连接类写法；只在被选为 `ai.knowledge` 时登记）：内核的 `PeriodicHealthContributor` 启动时同步探一次，之后按 `XiHan:AI:VectorData:HealthProbeIntervalSeconds`（有限的正数，默认 15；也是单次探测的超时，值不合法即 `ArgumentException` 启动失败）在后台重探。
  - 探针问向量存储默认集合（`XiHan:AI:Knowledge:Collection`）是否存在：一次轻量往返，存在与否都算可达；不列集合（按租户分集合时集合很多）、不建集合、不读写记录，不经管道。连接器不理会取消令牌时也按时限结束等待。
  - 判定：应答即 Ready；连接器抛出 → Degraded，`AI_UNAVAILABLE_002`（`ai.knowledge.unavailable`，`reason` 是异常类型的全名，2026-11-04，ADR-0111：这个 Provider 接任意连接器，异常消息可能带地址或连接串）；完整异常进日志，同一种失败第一次记 Warning，之后记 Debug；超时 → Degraded，`KERNEL_UNAVAILABLE_005`。没有 Failed：向量库不可达是外部条件，应用照常服务（readiness 通过、应用整体 Degraded），恢复后条目回到 Ready。
  - 条目不带 `Data` 与 `Description`，不写端点、集合名或任何连接信息；探针端点本来只输出错误码，原因只进日志与健康快照。

## 配置不热更新

`XiHan:AI` 的全部配置（`Providers`、`DefaultProvider` / `DefaultEmbeddingProvider`、`Prompts`、`Guardrails`、`Tools`、`Knowledge`）在装配时由 `AIOptions.FromConfiguration` 读一次、登记为单例，不支持热更新：改了要重启应用（ADR-0074）。框架不监听配置变化；`IAIProviderCatalog.Invalidate` 只丢弃缓存的客户端、用同一份选项重建（用于丢弃坏掉的连接），不拾取配置变化；提示词目录、工具目录（工具名在启动时校验）、护栏、知识库选项与提示增强器（提示词在启动时校验）都在创建时取定。应用替换的目录不受此限：它的 Provider 表与默认名由它自己维护，`IAIChat` 与知识库流水线每次调用都问目录（ADR-0110）。

理由：这些配置在装配与启动时被校验并被多个单例取用，热更新要么只部分生效（例如换了嵌入模型而向量集合的维度没变、换了提示词而启动期校验没有重做），要么要在运行中重做全部校验与重建，代价与风险都高；AI 配置的改动通常伴随部署，重启是可预期的生效点。

## 一致性

Provider 继承 `KnowledgeStoreConformance`（写入、按相似度排序、文档与元数据过滤、重写入替换、按文档删除、按块序号裁剪、集合隔离）与 `AIProviderConformance`（目录按名字解析聊天与嵌入、嵌入维度、`Invalidate` 后重建、未知名字 `AI_NOTFOUND_001`；默认名（2026-11-04）：夹具的 Provider 是聊天与嵌入的默认时两个默认名都是它、不写名字的解析得到与写名字相同的实例、`IAIChat` 不写 Provider 用它应答，没有默认时两者为 `null`、不写名字的解析与 `IAIChat` 都是 `AI_NOTFOUND_001`（带上面两个消息键）而写了名字照常，目录支持聊天与嵌入分开设默认时各按各的默认解析——不支持的目录不提供这个夹具，用例跳过）并通过全部用例；套件自带确定性的 `HashingEmbeddingGenerator` 与提供 `ai.embedding@1` 的 `HashingEmbeddingFeature`。

## 错误码

`AI_VALIDATION_001`–`002`、`AI_NOTFOUND_001`–`003`、`AI_DENIED_001`、`AI_TIMEOUT_001`、`AI_UNAVAILABLE_001`–`002`、`AI_UNEXPECTED_001`，见 `conventions/error-codes.md`。消息目录 `ai`，键 `ai.*`。
