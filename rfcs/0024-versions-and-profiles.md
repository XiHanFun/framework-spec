# RFC-0024 规范的版本与一致性档

> 状态：已采纳 | 日期：2026-11-19 | 对应 ADR：0242（门禁补漏）、0243 | 一致性档：`core`

## 摘要

规范以独立的语义化版本 `v1.x.y` 发布。规范性内容按一致性档划分，实现认领其中若干档，只对认领的档负责；SDK 的成熟度按认领的档判定。

## 动机

- README 承诺语义化版本标签与「`v1` 期间只增不改」，但规范仓库一个标签都没有。七个实现各自钉着裸提交，说不清自己实现的是哪一版。
- ADR-0233～0237 多次改写了各 SDK 的可观察行为，却没有任何版本号记录它。澄清与变更也从没区分过。
- 原来的「规范性（各语言必须一致）」把协议映射、打包、迁移和各子系统 RFC 都算了进去，而六个 SDK 只实现核心与插件一侧。按原来的定义，「Stable：通过全部向量」对 SDK 无从判定：WebAuthn、Wasm、远程 Provider 的向量本来就不归 SDK。

## 版本

1. **版本号**是 `MAJOR.MINOR.PATCH`，标签打在 `main` 上，规范本身打 `vX.Y.Z`。Go 的一致性模块在子目录 `conformance/` 里，Go 要求子目录模块的标签带目录前缀，所以同一提交另打 `conformance/vX.Y.Z`。
2. **大版本与线上的数字一致**：MAJOR 等于 `FrameworkInfo.SpecVersion`，也等于清单 `primitives` 所依赖的原语层大版本和 Schema `$id` 里的 `v1`。只有 `v2` 会改这些数字，那时与 `v1` 并存（RFC-0001「冻结」）。
3. **三级的界定**：
   - **PATCH**：不改任何规范性内容。包括措辞、示例、理由、非规范性文档，以及工具（运行器、`tools/speccheck`）的缺陷修复，前提是不改任何期望值。
   - **MINOR**：只增，以及把以前不作规定的行为写死。新增的形式有：新 RFC 与新章节、可选字段与可选操作、新档、新向量文件或新用例、运行器新用例。实现之间有分歧而规范没写的地方，选定一种写法也算 MINOR。约束有两条：
     - 写死不得让两个对端的互通失败：一边按同一大版本里较早的 MINOR 实现，另一边按新的 MINOR 实现。
     - 读取一侧对较早 MINOR 可能写出的形式要么照收，要么这次修订算 MAJOR。宿主必须容忍同一大版本里任一 MINOR 的插件。
   - **MAJOR**：改已经写明的行为、删除内容、线上不兼容。新的协议版本（如 `xihan.plugin.v2`）与旧版本并存时算 MINOR：宿主同时声明两个版本，由握手协商选定。去掉对旧版本的支持才算 MAJOR。
4. **协议版本**（`plugin/handshake.md` 的 `protocol_versions`）只在线上不兼容时新增一个整数版本。同一协议版本里的写死按第 3 条走规范的 MINOR：不升协议版本，也不在握手里协商 MINOR。
5. **预发布**：`v1.0.0` 之前打 `v1.0.0-rc.N`，rc 之间允许任何改动，逐条记进 `CHANGELOG.md`。`v1.0.0` 与 XiHan.Framework 的 5.0.0 正式版一起打，此后按第 3 条执行。
6. **变更记录**：每个改动规范性内容的提交，都在 `CHANGELOG.md` 的「未发布」一节记一条，标明 PATCH、MINOR 或 MAJOR 以及对应的 ADR。打标签时把「未发布」改成版本号。

## 实现钉规范

1. 日常分支可以指向规范已推送的任意提交（`dev` 或 `main`），即先改规范、再改实现。
2. 实现发预发布或正式版时，规范 submodule 必须正好在某个规范标签上；Go 的 `go.mod` 必须依赖 conformance 模块的标签版本，不能是伪版本。正式版只能钉规范的正式版标签（不带预发布后缀），预发布可以钉 rc 标签。各实现的发布工作流核对这一条。
3. 实现在 README 的「状态」一节写明三件事：钉的规范版本、认领的档、缺口。缺口指认领的档里没有回放的向量，逐条写理由。

## 一致性档

1. **档表** `conformance/profiles.json` 是唯一事实源。每个档列出规范文件、必须回放的向量与必须通过的运行器子命令。一个文件可以属于多个档；每个规范文件、每个向量文件都至少属于一个档。RFC 的状态行写明所属的档，与档表一致；`tools/speccheck` 与 conformance 模块的测试核对这两条。
2. **档名**：
   - `core`：所有实现都认领。
   - **角色档**：`plugin`（用本实现写进程外插件）；`host`（宿主：能力求解、进程外插件宿主、协议映射、应用清单与打包、版本迁移）；`wasm`（Wasm ABI，Experimental）。
   - **子系统档**：一个子系统 RFC 一档，用术语表的能力 ID 前缀命名，如 `persistence`、`caching`、`security`。
   - **远程 Provider 档**：`provider:<操作集>`，如 `provider:caching.distributed@1`。提供操作集的插件与宿主一侧的适配器都认领它，各自回放与本角色有关的部分。
3. 一个 RFC 的内容分属几个档时按章节归属，状态行列出全部所属的档。例如 RFC-0002 的读写属于 `core`，能力求解属于 `host`；RFC-0010 的模板与消息键属于 `core`，目录、区域协商与 Provider 属于 `localization`。
4. 新增档、把文件或向量加进已有的档都是 MINOR；把向量移出档是 MAJOR。
5. **读取档表**：Go 经 `conformance.Profiles()` 读内嵌的档表，`RequiredVectors(档…)` 给出认领这些档必须回放的向量。其他语言读 `spec/conformance/profiles.json`。

## 成熟度

| 级别 | 条件 |
| --- | --- |
| Reference | XiHan.Framework。认领 `core`、`host`、`wasm`、全部子系统档与它适配的 Provider 档，缺口逐条列出 |
| Stable | 认领 `core`；认领的每个 `stable` 档的向量都回放并通过；要求的运行器子命令都通过，且没有名单外的跳过；没有缺口；已有钉在规范正式版标签上的发布版 |
| Experimental | 认领 `core`，但有缺口，或还没有钉在规范标签上的发布版 |
| Community | 在 XiHanFun 之外维护 |

`experimental` 的档（目前是 `wasm`）不影响 Stable 的判定；但认领了就必须回放它的向量。

## 规范与决策记录

- 规范里的「ADR-NNNN」指 XiHan.Framework 仓库 `plans/adr/` 下以该编号开头的文件。
- 规范性的要求必须写在正文或向量里，不能只写在 ADR 里。ADR 记录取舍过程，实现规范的人不必读 ADR。

## 与 .NET 的映射

- `FrameworkInfo.SpecVersion` 是大版本 `"1"`。
- XiHan.Framework 的发布工作流核对 `framework/spec` 正好在规范标签上，随首个规范标签一起加上。
- 架构测试 `SpecVectorCoverageTests` 按认领的档核对向量。

## 非目标与未决

- 握手不携带插件实现的规范 MINOR。`SdkInfo` 已带 SDK 名与版本，诊断够用；需要时作为可选字段以 MINOR 加入。
- 不为规范的每个 MINOR 开维护分支：日常提交在 `dev`，`main` 由 `dev` 快进，标签打在 `main` 上。
- 以下按本 RFC 随后落地：七个实现的向量全集测试从豁免表改为读档表；发布工作流核对规范标签；首个标签 `v1.0.0-rc.1`。
