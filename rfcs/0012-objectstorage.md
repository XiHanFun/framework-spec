## 摘要

对象存储子系统只定义一个字节流级的 blob 契约：容器里按键存放不可变的字节与元数据。写入与删除以批量为主（单条是批量的特例），读取按键（可只读一段），列举按前缀分页。Provider 实现六个操作；分片上传与预签名是另两个可选能力。

## 能力

| 能力 | 含义 | 默认实现 |
| --- | --- | --- |
| `objectstorage.blob@1` | 容器 / 键 / 字节 / 元数据的对象存储，`IBlobStore` | `ObjectStorage.FileSystem`（本地目录，带配额） |
| `objectstorage.multipart@1` | 分片上传，`IBlobMultipartStore` | `ObjectStorage.FileSystem`（暂存目录）、`ObjectStorage.S3`（原生） |
| `objectstorage.presign@1` | 预签名地址，`IBlobUrlSigner` | `ObjectStorage.S3`（原生）；文件系统经 `Hosting.AspNetCore` 的宿主代收发 |

## 标识

- 容器 `ContainerName`：`^[a-z0-9][a-z0-9-]{1,61}[a-z0-9]$`（与 S3 桶名兼容）。
- 键 `BlobKey`：`/` 分段的路径，按 UTF-8 编码后 1 到 1024 字节（`BlobKey.MaxBytes`；2026-11-24 写明单位，ADR-0282：以前写「1 到 1024 个字符」，没有说按什么计，.NET 按 UTF-16 码元计，而 S3 的键上限是 1024 个 UTF-8 字节，含非 ASCII 字符的长键在文件系统存储上能写、在 S3 上被拒）；每段非空、不是 `.` 或 `..`；不含空白、控制字符与 `\`；区分大小写。
- 查询前缀 `BlobQuery.Prefix`（2026-11-24 写明，ADR-0282；以前正文没有写前缀的文法）：字符约束与字节上限同键（不含空白、控制字符与 `\`，按 UTF-8 编码后不超过 1024 字节），但可以为空（列举全部）、可以以 `/` 结尾，对各段不作要求（`a//b`、`./a` 只是筛选不到东西）；`BlobKey.IsValidPrefix` 判定，不合法在构造 `BlobQuery` 时抛出 `ArgumentException`。
- 孤立的代理项（2026-11-26 修订，ADR-0316；以前键与查询前缀只排除空白、控制字符与 `\`，保存的文件名只排除控制字符，上传标识只排除空白与控制字符，孤立的代理项都算合法的字符）：对象键、查询前缀、预签名下载地址上保存的文件名（「范围读取、分片上传与预签名」）与分片上传的上传标识都不能含孤立的代理项；自定义元数据的值同样不能含（2026-11-27 修订，ADR-0322；以前值只排除控制字符）。容器名、元数据名、实例名与内容类型的文法只有 ASCII，本来就排除了它。
  - 孤立的代理项是不在一对之中的 U+D800–U+DFFF 码元：单独的高代理项（U+D800–U+DBFF）、单独的低代理项（U+DC00–U+DFFF）、低代理项在前的颠倒的一对、末尾没有低代理项跟着的高代理项。高代理项紧跟着低代理项是成对的代理项，即平面以外的一个字符（如 U+1F600），照常合法，长度按它的 4 个 UTF-8 字节计。
  - 以 UTF-16 表示字符串的实现（.NET、Java、JavaScript）照上一条逐个码元判定；以码位表示字符串的实现（Python）里不能有 U+D800–U+DFFF 的码位；以字节表示字符串的实现（Go、PHP）里这几种标识必须是合法的 UTF-8，孤立的代理项在那里只能以编成 UTF-8 的代理项（`ED A0 80`–`ED BF BF`）或别的非法字节序列出现，同样拒收。
  - 理由：这几种标识都要编成 UTF-8 字节或 URL：S3 的对象键与请求、文件系统存储的路径、宿主代签地址的路径与查询串、签名的规范串、`Content-Disposition` 头。孤立的代理项编不成 UTF-8，宽松的编码器把它换成 U+FFFD，不同的标识因此撞成同一个，签名也对上了另一个对象。例如给键 `a\uD800` 签出的宿主地址经百分号编码成了 `a%EF%BF%BD`，打开的是对象 `a�`；规范串经宽松编码之后与给 `a�` 签的字节相同，所以验签通过。元数据的值进文件系统存储的元数据文件（JSON，编成 UTF-8）与 S3 的 `x-amz-meta-*` 请求头：.NET 的文件系统存储实测写入结果里是原值、读回的是 U+FFFD（`a\uD800b` 读回 `a�b`），把读出的元数据原样写回也得不到原来的值；按 UTF-8 写请求头的 S3 客户端同样把它换成 U+FFFD（ADR-0322）。
  - 不合法与各自的其余文法同样处理：构造时抛出 `ArgumentException`，`BlobKey.IsValid`、`BlobKey.IsValidPrefix` 为假；元数据的值有孤立的代理项时给 `BlobPutOptions.Metadata` 赋值即抛出，同值里有控制字符。
- 保留前缀（2026-11-01 增补，ADR-0090）：首段是 `.xihan` 的键（`.xihan` 本身与 `.xihan/…`，区分大小写，`BlobKey.ReservedSegment`）留给框架自己的对象（如 S3 的条件写入探测键），不在键文法之内：构造时抛出 `ArgumentException`，`BlobKey.IsValid` 为假，业务写不进、读不到、删不掉；各 Provider 列举时跳过存储里已有的这类对象（框架经底层客户端写入的，或从外部放入的），不出现在业务列举里。查询前缀 `BlobQuery.Prefix` 只是筛选，不受此限，以 `.xihan` 开头的前缀列举总是空的。
- 自定义元数据名：`^[a-z0-9][a-z0-9-]{0,63}$`；值不含控制字符（含 CR、LF）与孤立的代理项（见上一条，2026-11-27 修订，ADR-0322），成对的代理项照常合法；名与值合计不超过 2048 个 UTF-8 字节（`BlobPutOptions.MaxMetadataBytes`，与 S3 用户元数据的上限一致）。2026-11-13 修订，ADR-0214；以前值为任意字符串、不限大小，换行进了 S3 的请求头与文件系统的元数据文件，一个对象的元数据可以无限大。
- 内容类型 `BlobPutOptions.ContentType`（2026-11-13 修订，ADR-0214；以前只要求不空白）：媒体类型 `type/subtype`，两段都是 HTTP 的 token 字符，可跟若干个 `;` 起头的参数，整体 1 到 255 个字符（`MaxContentTypeLength`；内容类型只有 ASCII，字符数即字节数），`BlobPutOptions.IsValidContentType` 判定。参数的写法照 RFC 9110 §5.6.6 的 `parameters = *( OWS ";" OWS [ parameter ] )`（2026-11-25 修订，ADR-0295；2026-11-24 的 ADR-0282 曾要求每个 `;` 之后必须有参数，`text/plain;`、结尾多出的 `;` 与连续的 `;` 不合法，宿主代收的上传回 400；RFC 9110 的参数本来可以为空，野外也有客户端这样发；再往前 `;` 之后可以为空，媒体类型与 `;` 之间的空格正文没有写而 .NET 照收）：
  - 每个 `;` 两侧可以有空格，即 RFC 9110 的 OWS；只取其中的空格，制表符是控制字符（ADR-0214），在 `;` 的哪一侧都不收。
  - 每个 `;` 之后的参数可以为空：`text/plain;`、`text/plain ;`、结尾多出的 `;`（`text/plain; charset=utf-8;`）与连续的 `;`（`text/plain;;charset=utf-8`、`text/plain; ;charset=utf-8`）都合法。
  - 不为空的参数是不含 `;` 的可打印 ASCII 与空格（U+0020–U+007E），以非空格字符开头；参数内部不再细分：不要求 `name=value`，也不解析引号，引号里的 `;` 同样算分隔（`boundary="a;b"`、`boundary=";;"` 都合法）。
  - 媒体类型之后只有空格、没有 `;` 的不合法（`text/plain `）：OWS 只出现在 `;` 两侧。
  - 整串不以空格结尾（2026-11-26 修订，ADR-0308；以前以空格结尾的写法合法，如 `text/plain; charset=utf-8 `，2026-11-25 的 ADR-0295 起还有 `text/plain; `、`text/plain ; ` 与 `text/plain; charset=utf-8; `）。内容类型最终是 HTTP 的字段值——S3 的 `Content-Type` 请求头与响应头、预签名上传与宿主代收发的 `Content-Type`——而 RFC 9110 §5.5 的字段值不含首尾空白，收发的一方遇到首尾的空白要先去掉，所以任何靠 HTTP 头存内容类型的存储都存不住结尾的空格，做不到「契约」的原样存取（RustFS 1.0.6 上实测：经预签名地址原样发出的 `text/plain; ` 读回是 `text/plain;`，`text/plain; charset=UTF-8 ` 读回去掉了结尾的空格）。这一条对所有存储都成立，不只是 S3：文件系统存储自己存得住，但同一个值经宿主代收发、预签名地址或换一个存储都要过 HTTP 头，合法的内容类型应当在哪条路上都是同一个值。`;` 之后的空格因此只在后面还有字符时才合法：`text/plain ;`、`text/plain; charset=utf-8 ;`、`text/plain;  ;` 合法，`text/plain; `、`text/plain;  `、`text/plain ; ; ; `、`text/plain; charset=utf-8 ` 不合法。开头的空白本来就不合法（媒体类型以 token 字符开头）；空格之外的空白（制表符、换行）在哪里都不收。
  - 文法按整串匹配：`^<token>/<token>( *;([\x20-\x7E]*[\x21-\x7E])?)?$`，`<token>` 是一个或多个 token 字符（2026-11-26 修订，ADR-0308；以前是 `^<token>/<token>( *;[\x20-\x7E]*)?$`）。即第一个 `;`（之前可以有空格）之后为空，或是最后一个字符不是空格的一串可打印 ASCII 与空格；它就是以前的集合去掉以空格结尾的，与按上面几条逐段写出的 `^<token>/<token>( *; *([\x21-\x3A\x3C-\x7E][\x20-\x3A\x3C-\x7E]*)?)*$` 再加上「最后一个字符不是空格」是同一个集合（任意一串可打印 ASCII 与空格都能在每个 `;` 处切成可以为空的参数），实现取哪一种都可以。
- 标识不合法在构造时抛出 `ArgumentException`（编程错误），不进入 Provider。

## 契约

| 操作 | 语义 |
| --- | --- |
| `Put(container, uploads[])` | 按顺序逐项写入；每项带键、内容流与选项（内容类型、自定义元数据、是否允许覆盖）；返回逐项结果（元数据或错误）。空列表返回空；重复键按顺序各执行一次 |
| `Get(container, key)` | 打开内容流与元数据；不存在为 `OBJECTSTORAGE_NOTFOUND_001` |
| `Get(container, key, range)` | 只读一段字节（见下文「范围读取、分片上传与预签名」） |
| `Head(container, key)` | 只取元数据 |
| `Delete(container, keys[])` | 按顺序逐项删除；返回逐项结果（是否存在，或错误）；重复键第二次报告不存在 |
| `List(container, query)` | 按前缀列举，键的序数顺序，`PageSize`（1–1000，默认 1000）分页，`ContinuationToken` 不透明；`PageSize` 越界不在构造时抛出，返回 `OBJECTSTORAGE_VALIDATION_005`（HTTP 400，参数 `pageSize`、`max`），不访问存储。不符合键文法的对象（保留前缀下的、S3 的目录占位）跳过，所以一页可能少于 `PageSize` 条、甚至为空而仍带续页标记，调用方取到续页标记为空为止 |

- 元数据 `BlobMetadata`：键、长度、内容类型（默认 `application/octet-stream`）、`ETag`（内容变化即变化）、最后修改时间、自定义元数据。写入结果（`Put` 逐项返回的元数据）里的最后修改时间是 Provider 记下的写入时刻，不要求与之后读出的相同：文件系统存储存的就是它；S3 的写入应答本来不带修改时间，取本机收到应答时的时钟，读取、`Head` 与列举交出服务记下的值（2026-11-26 写明，ADR-0313；以前不作规定，一致性套件比较写入结果与读出的元数据时本来就不比修改时间）。要服务记下的时刻就在写入之后再 `Head`（2026-11-27 写明，ADR-0322：维持本机时钟，`LastModified` 仍是必有的值）。
- 内容类型原样存取（2026-11-25 写明，ADR-0295；以前不作规定）：写入（含分片上传的发起）把 `ContentType` 原样交给存储，读取把存储里的值原样放进 `BlobMetadata.ContentType`，Provider 自己不规范化——不去掉空参数，不改 `;` 两侧的空格，不改大小写。把读出的元数据原样写回（复制对象之类）得到同一个内容类型。所用的存储客户端写不出原值的（它会改写这个值），在发出任何请求之前以 `OBJECTSTORAGE_VALIDATION_007` 失败（HTTP 400，参数 `contentType`），不改写之后照写；预签名上传限定的内容类型由客户端自己发送，不经 Provider 的客户端，不受此限。S3 的情况见「S3 Provider」。
- 存储收不下或会改写的自定义元数据（2026-11-27 写明，ADR-0343；以前不作规定）：写入（含分片上传的发起）把合「标识」的自定义元数据交给存储，读取把存储里的名与值原样放进 `BlobMetadata.Metadata`。有两类 Provider 可以拒收，文件系统存储两类都不会遇到：
  - 存储按它自己的计法判定元数据超过上限（如按编码之后的字节数计），拒收名与值合计不超过 2048 个 UTF-8 字节（按原值计）的元数据：写入与分片上传的发起以 `OBJECTSTORAGE_VALIDATION_008` 失败（HTTP 400，没有参数），不当作存储故障；Provider 不预先按编码之后的长度拒收，契约的上限按原值计。
  - 所用的存储会把某种值存成另一个值、读回的不是写入的值：写入与分片上传的发起在发出任何请求之前以 `OBJECTSTORAGE_VALIDATION_009` 失败（HTTP 400，参数 `name` 是那一项的元数据名，不带值），不改写之后照写，同内容类型的 `OBJECTSTORAGE_VALIDATION_007`。
  - S3 的情况见「S3 Provider」的「自定义元数据的值」。
- `Overwrite = false` 且已存在 → `OBJECTSTORAGE_CONFLICT_001`，不写入。不覆盖写入必须原子：多个写入方同时以 `Overwrite = false` 写同一个新键，恰好一个成功，其余都是 `OBJECTSTORAGE_CONFLICT_001`，不能先查是否存在再写（并发时后写的会静默覆盖先写的）；做不到的存储不能声称支持不覆盖写入（S3 见下文「S3 的条件写入探测」）。
- 容器按需创建（文件系统）或由 Provider 的基础设施预先存在（S3 桶）；契约不管理容器。
- 基础设施失败（IO、网络）→ `OBJECTSTORAGE_UNAVAILABLE_001`，`reason` 只写异常类型的全名，完整异常进日志（2026-11-04，ADR-0115）：IO 异常的消息常带服务器上的完整路径；配额或单对象大小超限 → `OBJECTSTORAGE_UNAVAILABLE_002`，不写入。
- 批量操作在两项之间检查取消；已完成的项不回滚。
- 写入是原子的：读取方要么看到旧对象，要么看到完整的新对象。

单条便捷方法（`BlobStoreExtensions`）：`Put(container, key, stream | bytes, options)`、`Delete(container, key)`、`Exists`、`ReadAllBytes`，都转调批量方法。

## 默认实现

`ObjectStorage.FileSystem`：根目录（默认 `<AppContext.BaseDirectory>/blobs`）下 `<container>/data/<key>` 存内容、`<container>/meta/<key>.json` 存元数据；写入先落临时文件再原子替换，不覆盖的写入（含分片上传的完成）由文件系统原子判定谁先占住内容路径，目标已存在即 `OBJECTSTORAGE_CONFLICT_001`，多个写入方（含共享目录的多个进程）只有一个成功：Unix 上先以独占创建（`O_CREAT | O_EXCL` 语义）的空文件占位，再以 `rename` 把内容原子替换上去，不能用「先查目标再改名」的不替换移动，.NET 在 Unix 上的 `File.Move(…, overwrite: false)` 就是这样实现的（2026-11-11 修订，ADR-0168）；Windows 上用不替换的改名（`MoveFileEx` 不带替换标志，本身原子），不用占位再替换——替换要求目标此刻没有被打开，并发写入方探测占位文件的那一下就让占到位的一方失败（2026-11-12 修订，ADR-0172）；`ETag` 是内容的 SHA-256；配额 `MaxTotalBytes`（默认 1 GiB）与 `MaxBlobBytes`（默认 256 MiB），启动时扫描目录得到已用量，之后在进程内计量；单进程正确，多进程共享目录时配额只是近似。写入边复制边在进程内预留额度，总配额按已用量加全部预留判定，并发写入合计不超过它；覆盖期间新旧内容同时在盘上，预留按新内容的全长，旧对象的字节到提交时才释放。提交（改名）、删除与记账在同一把锁里完成，按此刻磁盘上旧内容的实际长度计算差值，并发覆盖与删除同一个键时用量与磁盘一致（2026-11-12 修订，ADR-0183；以前只检查不预留，并发写入能超额最多 N×`MaxBlobBytes`，并发覆盖按开始时读到的旧长度扣减会少记用量）。存储只经 `FileSystemBlobStore.CreateAsync` 创建：建目录、扫描已用量并清掉过期的分片上传后才交出，不提供不初始化的公开构造，否则配额从零算起会放过超额写入（2026-11-11 修订，ADR-0163）。

读取与覆盖、删除交错（2026-11-18 修订，ADR-0241）：

- 正在读的对象照样能覆盖与删除，读取方读完的是打开时的那一版；被换掉或删掉的旧内容在最后一个读取方关闭之前仍占磁盘，不计入用量。读取方打开内容与元数据都容许删除共享。Windows 上普通的替换改名（`MoveFileEx` 带替换标志）换不掉正被打开的文件，读取方容许删除共享也不行，所以替换以 POSIX 语义改名（`FILE_RENAME_FLAG_POSIX_SEMANTICS`）；卷不支持这种改名时（SMB 共享、FAT 等）退回普通的替换改名并记一次警告，正被读取的对象覆盖时仍以 `OBJECTSTORAGE_UNAVAILABLE_001` 失败。Unix 的 `rename` 本来就与目标是否被打开无关。
- 一次读取（`Get`、`Head`、列举的每一项）拿到的元数据与内容属于同一版：提交与删除在记账的同一把锁里成对变更内容与元数据，读取不进锁、读完核对期间有没有变更，有就在锁里重读。以前先读元数据、再打开内容，两步之间被覆盖时元数据（长度、`ETag`）是上一版、内容是下一版；两步之间被删时报 `OBJECTSTORAGE_UNAVAILABLE_001` 而不是不存在，列举整页失败。
- 这两条只在进程内成立：多个进程共享目录时与配额一样只是近似。

## S3 Provider

`ObjectStorage.S3`：容器即桶，键即对象键，经 AWS SDK 访问 Amazon S3 与兼容服务（MinIO、阿里云 OSS、腾讯云 COS、Cloudflare R2 等），不再为每家云单独做包。

- 云厂商的兼容服务（2026-11-01 增补，ADR-0090）：阿里云 OSS、腾讯云 COS、Cloudflare R2 等同样只用这一个包，不为各家的私有请求头（如 OSS 的 `x-oss-forbid-overwrite`、COS 的 `x-cos-forbid-overwrite`）做适配，不覆盖写入只认标准的 `If-None-Match: *`。这几家是否认它框架没有实测，接入前要实测：缺省的条件写入探测就是实测（下文「S3 的条件写入探测」），不认时启动失败（`OBJECTSTORAGE_UNAVAILABLE_003`）或之后在健康项上报告；也可以按探测的做法用 curl 发两次带 `If-None-Match: *` 的 `PutObject`，第二次必须 412。不认就设 `ConditionalWrites = false`，后果是 `Overwrite = false` 的写入与分片上传的发起、完成一律 `OBJECTSTORAGE_UNAVAILABLE_003`，"只在不存在时写入"不再可用——需要它的业务改用不会冲突的键（如带随机后缀）或改为覆盖写入，框架不退回先查再写。
- `Overwrite = false` 先 `Head`（已存在就不必上传内容）再带 `If-None-Match: *` 写入，由服务端保证原子；已存在 → `OBJECTSTORAGE_CONFLICT_001`。服务是否认条件写入要先探明（见下文「S3 的条件写入探测」）：探明之前不覆盖写入返回不可用，探明不认的服务（如 Garage、Zenko CloudServer）上不覆盖写入一律报错，启动时就探明的启动失败，任何时候都不带着可能静默覆盖的不覆盖写入运行。不可定位的内容流先落临时文件取得长度，不整体装进内存。
- 批量删除：S3 不报告对象是否存在过，先逐键 `Head` 定存在性（同一批里重复的键只有第一次算存在），再把存在的键按每批 1000 个 `DeleteObjects`；删除失败只影响本次负责删除的项。`DeleteObjects` 以静默模式发出，应答只列错误项；有错误项没有键（缺失或为空），或带的键不在这一批里，就认不出是哪一项失败，是不合规的应答：这一批里本次负责删除的项各以 `OBJECTSTORAGE_UNAVAILABLE_001` 失败，同这一批的请求整个失败，`reason` 写明是批量删除的应答有认不出键的错误项，不带应答里的值；已确认不存在的项、同一批里重复的项与别的批照旧（2026-11-26 写明，ADR-0313；以前 .NET 以空键写进逐项的结果，抛出 `ArgumentNullException`，而这时这一批的删除已经执行了）。AWS SDK for .NET 4.0 在 `DeleteObjects` 的应答有错误项时不交出应答，而是抛出带着解出的应答的 `DeleteObjectsException`（静默模式也是，不重发），Provider 从它带的应答里取错误项，照上面逐项报告或整批报告（2026-11-27 写明，ADR-0333；以前 .NET 把这个异常当作存储故障，这一批要删的项都以 `OBJECTSTORAGE_UNAVAILABLE_001` 失败、`reason` 是这个异常类型，按错误项逐项报告只有测试替身走得到）。这样报错的项里可能有已经删掉的：删除是幂等的，调用方重试，已删的报告不存在。
- 内容类型（2026-11-25 写明，ADR-0295）：.NET 参考实现经 AWS SDK for .NET 写入，SDK 把 `Content-Type` 交给 .NET 的媒体类型解析器（`MediaTypeHeaderValue`）重新写出。它解析不了的（`;` 之后为空，未加引号的参数值里有空格等），SDK 抛出 `FormatException`，而这时请求行与其余请求头已经发出（不带 `Content-Type`）；解析得了而写法不同的，它一律写成 `type/subtype; 参数`（`;` 之前没有空格、之后一个空格），线上发的是改写后的值，而签名（SigV4）按原值去掉首尾空白、把连续的空格合并成一个之后计算，服务按收到的值同样处理后验签（2026-11-26 修订，ADR-0308；以前写的是「签名按原值计算，服务验签对不上」，没有分出只差在连续空格的一类）：
  - 合并空格之后仍与改写后的值不同的（`;` 之后没有空格的 `text/plain;charset=UTF-8`，`;` 之前有空格的 `text/plain ;charset=UTF-8`），验签对不上，请求被拒绝。
  - 只差在连续空格的（`text/plain;  charset=UTF-8`），验签通过，服务存下的是改写后的 `text/plain; charset=UTF-8`，不报错。结尾的空格在签名时同样被去掉，服务存下去掉之后的值；以空格结尾的内容类型已不合文法（见「标识」），到不了 Provider。
  - 以上（含解析不了时 SDK 抛出之后请求照样发出、服务回 403 而没有存下）是对 RustFS 1.0.6 的实测（AWS SDK for .NET 4.0，经 http；被拒绝的回 403 `SignatureDoesNotMatch`）；Amazon S3 没有实测，按 SigV4 的规范请求头（值去掉首尾空白、连续空格合并成一个）推断结果相同，其余兼容服务未知。
  - 两类都写不出原值：写入与分片上传的发起一律返回 `OBJECTSTORAGE_VALIDATION_007`，不发请求（按「契约」的内容类型原样存取）。不拒绝的话，解析不了的抛出异常，前一类请求被拒，后一类悄悄存下别的值。
  - 写得出原值的照常写入（如 `text/plain`、`text/plain; charset=utf-8`、`Text/HTML`、`text/plain; boundary=";;"`）。
  - 读取时 SDK 同样按这个写法交出它解析得了的值：存储里的 `text/plain;charset=utf-8`（例如经预签名地址由浏览器上传的）读出 `text/plain; charset=utf-8`，解析不了的原样交出——读取一侧 .NET 的 S3 Provider 做不到原样，是已知的缺口。
- 自定义元数据的值（2026-11-27 写明，ADR-0333；以前 .NET 把值原样写进 `x-amz-meta-*` 请求头：值里有非 ASCII 字符时 .NET 的 HTTP 客户端不发出这个头，写入与分片上传的发起以 `OBJECTSTORAGE_UNAVAILABLE_001` 失败；首尾的空格被 HTTP 去掉，读回的少了它们）：S3 的用户元数据经 HTTP 头存取，头值只能是可打印 ASCII 与空格，首尾的空白不算在值里（RFC 9110 §5.5）。Provider 照 RFC 2047 把头写不出原样的值编成 encoded-word、读回时解码，「标识」允许的值（不含控制字符与孤立的代理项）因此除了写入时拒收的一类（下一条）都能原样存取（2026-11-27 修订，ADR-0343；以前没有拒收的一类）。
  - 写入（含分片上传的发起）：值里有 U+0020–U+007E 之外的字符（非 ASCII），以空格开头或结尾，或以 `=?` 开头且以 `?=` 结尾（原样写出，读回时会被当作 encoded-word；RustFS 1.0.6 还会拒收它解不了的这类值，见下「服务怎么存」），就把它编成 UTF-8 字节，以 B 编码写成 `=?UTF-8?B?<base64>?=`。一个 encoded-word 不超过 75 个字符（RFC 2047 §2），即至多带 45 个字节；超过的在 UTF-8 字符的边界处拆成几个，按次序以一个空格隔开，不把一个字符（含平面以外字符的 4 个字节）拆在两个 encoded-word 里。其余的值（可打印 ASCII，中间可以有空格，含空串）原样写，写入结果里的元数据是原值。整个是 encoded-word 形状的只有 ASCII 的值（判定同下面「读回」里解码的形状，如 `=?UTF-8?B?5Lit?=`、`=?UTF-8?B?5Lit?= =?UTF-8?Q?x?=`）不写：写入与分片上传的发起以 `OBJECTSTORAGE_VALIDATION_009` 失败，参数 `name` 是第一个这样的元数据名（按名的序数次序），不发请求，排在内容类型的核对之后、不覆盖写入的放行与 `Head` 之前（见「契约」）；以 `=?` 开头且以 `?=` 结尾而不是这个形状的只有 ASCII 的值（如 `=?x?=`）照旧编码之后写出（2026-11-27 修订，ADR-0343；以前整个是 encoded-word 形状的值同样编码之后写出：Amazon S3 照它的文档先解码 Provider 写出的 encoded-word、存下只有 ASCII 的原值并原样返回，读回时又被解码，悄悄变成另一个值）。
  - 读回（读取与 `Head`）：值整个是以线性空白（空格与制表符）隔开的一个或多个 encoded-word 时解码。encoded-word 照 RFC 2047 §2 写成 `=?charset?encoding?encoded-text?=`：charset 与 encoding 是 RFC 2047 的 token（不含空格、控制字符与 especials），encoded-text 是 `?` 与空格之外的可打印 ASCII，至少一个字符。相邻 encoded-word 之间的空白忽略（RFC 2047 §6.2），各个解出的字节按次序连起来再按 UTF-8 解码，一个字符被拆在两个 encoded-word 里也照常解出；charset 不区分大小写，只认 `UTF-8`（可带 RFC 2231 的 `*语言` 后缀）；encoding 认 `B` 与 `Q`，不区分大小写，`Q` 里 `_` 是空格、`=` 之后两位十六进制数字（不区分大小写）是一个字节；单个 encoded-word 超过 75 个字符照常解码。不是这样的只有 ASCII 的值原样交出，包括只有一部分是 encoded-word 的（`note =?UTF-8?B?5Lit?=`）与相邻的 encoded-word 之间没有空白的。
  - 读回时值里有 U+0080 及以上的字符（2026-11-27 写明，ADR-0343；以前 .NET 原样交出 HTTP 客户端给的字符串）：这是别的写入方不按 RFC 2047、直接把 UTF-8 字节写进 `x-amz-meta-*` 头，服务又原样返回的字节，不是 encoded-word。.NET 的 HTTP 客户端（`SocketsHttpHandler`，Provider 建的两种传输都是，AWS SDK 原样转交）把应答头里 0x80–0xFF 的每个字节读成一个 U+0080–U+00FF 的字符（Latin-1），不替换、不抛出（回环上的假对端实测，合法与不合法的 UTF-8 字节都是这样）；Provider 把这些字符还原成字节，严格按 UTF-8 解出原值，再过控制字符的核对，不交出乱码。有 U+00FF 之外的字符说明不是这样交来的（应用注册了按别的编码读头的客户端），还原不了。只有 ASCII 的值照上一条判是不是 encoded-word，不变。
  - 解不了的是不合规的应答，读取与 `Head` 返回 `OBJECTSTORAGE_UNAVAILABLE_001`，`reason` 写明是哪一步的应答里有解不了的 encoded-word 或原样的字节，不带应答里的值，记一条 Warning；不原样交出编码的文本，也不交出替换过的字符：charset 不是 UTF-8，encoding 不是 `B` 或 `Q`，`B` 的文本不是带补齐的 base64，`Q` 的 `=` 之后不是两位十六进制数字，连起来的字节不是合法的 UTF-8，或解出的值含控制字符（「标识」不允许）；原样写进头的字节不是合法的 UTF-8（含编成 UTF-8 的代理项）、解出的值含控制字符（U+0085 之类的 C1 控制字符也算），或有还原不了的字符，同样如此（2026-11-27 写明，ADR-0343）。
  - 服务怎么存：Amazon S3 的文档写明，值里有非 US-ASCII 字符时按 RFC 2047 解码之后存下，返回时再按 RFC 2047 编码，只有 US-ASCII 的值原样返回；RustFS 1.0.6 原样存取（实测：存下的就是 Provider 写出的 encoded-word，读回同样的文本）。Provider 写出的总是只有 US-ASCII 的值，两种服务读回的都是 encoded-word，照上一条解出原值。RustFS 1.0.6 上另实测：首尾的空格不编码时被去掉，中间的连续空格与空串原样往返，编码之后约 3.3 KB 的元数据照收。别的写入方直接写进头的 UTF-8 字节（2026-11-27 实测，ADR-0343）：RustFS 1.0.6 读回时把有非 ASCII 字符的值照 RFC 2047 编成 encoded-word（B 编码，每 45 个字节一个、以一个空格隔开，与 Provider 写出的同一个形状），Provider 照「读回」解出原值，只有 ASCII 的原样返回；原样返回字节的服务按上面的原始字节解出，其余兼容服务未知。以 `=?` 开头且以 `?=` 结尾的只有 ASCII 的值原样写进头时（2026-11-27 实测，ADR-0343）：RustFS 1.0.6 把它当作 encoded-word 去解，解得了的（`=?UTF-8?B?YQ==?=`）原样存下、原样读回，解不了的（`=?x?=`、`=?foo?=`、`=?UTF-8?X?abc?=`、`=?UTF-8?B?5Li?=`、`=?UTF-8?B?5Lit?==?UTF-8?B?5paH?=` 等）以 400 `InvalidArgument` 拒收，所以 Provider 编码之后写出这类值。
  - Amazon S3 没有实测，下面两条照它的文档定（2026-11-27 修订，ADR-0343；以前写作两处可能的缺口，前者按存储故障返回 `OBJECTSTORAGE_UNAVAILABLE_001`，后者编码之后写出、读回时变成另一个值）：
    - 用户元数据上限（2 KB）按请求头里各键与值的 UTF-8 字节数计，编码之后的值比原值长（base64 是原来的 4/3，每 45 个字节另加 13 个字符），原值离「标识」的 2048 字节上限不远、非 ASCII 的字节又多时，服务以 400 `MetadataTooLarge` 拒收：写入与分片上传的发起返回 `OBJECTSTORAGE_VALIDATION_008`（见「契约」；.NET 经 AWS SDK for .NET 4.0 得到 `ErrorCode` 为 `MetadataTooLarge` 的 `AmazonS3Exception`，SDK 不重发，回环上的假对端实测）。不预先按编码之后的长度拒收：契约的上限按原值计，文件系统存储与 RustFS 都收得下。
    - 整个是 encoded-word 形状的只有 ASCII 的值写入时拒收（见上「写入」）：Amazon S3 先解码 Provider 写出的 encoded-word、存下这个只有 ASCII 的原值并原样返回，读回时它又被当作 encoded-word 解码。
    - 仍有一处可能的缺口：以空格开头或结尾的只有 ASCII 的值，Provider 编码之后写出，Amazon S3 若同样先解码、存下原值并原样返回，HTTP 去掉首尾的空白，读回的少了它们；RustFS 原样存取 encoded-word，不受影响。
  - .NET 参考实现不用 AWS SDK for .NET 的 `AWSConfigsS3.EnableUnicodeEncodingForObjectMetadata`：它是进程级的全局开关，逐个 UTF-16 码元做百分号编码（把成对的代理项拆成两个码元分别编码，结果不是合法的 UTF-8 百分号编码），也不是 S3 的约定。
- 列举经 `ListObjectsV2`（S3 保证键的序数顺序），续页标记是其 continuation token；条目只有键、长度、`ETag` 与修改时间，内容类型为默认值、自定义元数据为空，需要时再 `Head`——列举条目的元数据因此是"可能不完整"的，一致性套件只校验键顺序、长度与 `ETag`。不符合键文法的对象（以 `/` 结尾的"目录"占位）跳过。应答说截断了（`IsTruncated`）却没有可用的续页标记 `NextContinuationToken`（缺失、为空，或与本次请求带的相同，拿它再列只会回到原处），或要交出的对象没有可用的 `ETag`（判定同下一条）、没有修改时间、没有长度 `<Size>` 或长度为负（长度 2026-11-27 写明，ADR-0322；以前缺 `<Size>` 时 .NET 按 0 交出），是不合规的应答：整页返回 `OBJECTSTORAGE_UNAVAILABLE_001`，不交出续页标记为空、看上去已经列完的一页，也不跳过那个对象；`reason` 写明缺的是什么，不带应答里的值（2026-11-26 写明，ADR-0313；以前截断而没有续页标记时交出续页标记为空的一页，调用方以为列完了；对象缺 `ETag` 时元数据的 `ETag` 是空串，缺修改时间时是 .NET 的最小时刻）。跳过的对象（目录占位、保留前缀下的）缺什么不影响这一页。
- 读取、`Head` 与写入的应答里的 `ETag`、修改时间与长度（2026-11-26 写明，ADR-0313；以前缺 `ETag` 时元数据的 `ETag` 是空串，缺修改时间时是 .NET 的最小时刻，都是静默兜底；长度 2026-11-27 写明，ADR-0322）：照 Amazon S3 API Reference，`GetObject`（含范围读取的 206）与 `HeadObject` 的应答带 `ETag`、`Last-Modified` 与 `Content-Length` 头，`PutObject` 的应答带 `ETag` 而本来没有修改时间。
  - 本该有却没有可用的值是不合规的应答：`ETag` 缺失、为空，或去掉两端的引号之后为空或只有空白（RFC-0001「空白字符」）；修改时间缺失。读取、`Head` 与写入返回 `OBJECTSTORAGE_UNAVAILABLE_001`，`reason` 写明是哪一步的应答缺了什么，不带应答里的值。写入不重发、不回滚：对象可能已经写进去了，调用方可以 `Head`，或重写同一个键。
  - 长度（2026-11-27 写明，ADR-0322；以前缺 `Content-Length` 时 .NET 取 HTTP 客户端给的值，没有就是 0，交出一个长度为 0 的非空对象）：整读（200）与 `Head` 的应答里 `Content-Length` 就是对象的长度，缺失或为负是不合规的应答，同上一条返回 `OBJECTSTORAGE_UNAVAILABLE_001`；范围读取起点越界时为取总长而发的 `Head` 同此，不以 0 写进 `OBJECTSTORAGE_VALIDATION_001` 的参数。范围读取（206）的总长取自 `Content-Range`（缺失或解析不了即服务忽略了范围，同样是 `OBJECTSTORAGE_UNAVAILABLE_001`），不用 `Content-Length`。
  - SDK 解析不了的应答（2026-11-27 写明，ADR-0322；以前 .NET 把 AWS SDK 解组时抛出的 `FormatException`、`OverflowException` 原样抛给调用方）：应答头或响应体里有 SDK 要按类型读的值写错了——`Last-Modified` 不是日期，`Content-Length`、`x-amz-mp-parts-count` 不是数或超出范围，布尔值的头不是 `true` / `false`，列举与列出分片里的 `<Size>`、`<PartNumber>` 不是数，等等——是不合规的应答；响应体不是良构的 XML（列举、列出分片、批量删除、发起与完成分片上传的应答）同此（2026-11-27 写明，ADR-0333；以前 .NET 把 SDK 抛出的 `XmlException` 原样抛给调用方）。读取、`Head`、写入、批量删除、列举与分片上传的每一步都返回 `OBJECTSTORAGE_UNAVAILABLE_001`，`reason` 写明是哪一步的应答解析不了，不带应答里的值，不重发；批量删除按一批计，同这一批的请求整个失败。放弃分片上传与建桶（`EnsureBuckets`）的成功应答现在没有 SDK 按类型读的值，同样按这一条处理，`reason` 点名 `AbortMultipartUpload` 或 `PutBucket`（2026-11-27 写明，ADR-0333；以前 .NET 不接这两步的解析异常，SDK 以后在这两个应答里按类型读值就会漏出来）。.NET 参考实现只认 SDK 解组时的这三类异常：`FormatException`（`UriFormatException` 除外，它来自端点而不是应答）、`OverflowException` 与 `XmlException`（2026-11-27 起，ADR-0333）；Provider 发出的请求里的值都已按各自的文法核对过（内容类型见上「内容类型」），SDK 在请求一侧不会因它们抛出这两类异常。
  - 整读的 `ETag` 不是十六进制同样是不合规的应答（2026-11-26 写明，ADR-0317；以前 SDK 抛出的 `ArgumentOutOfRangeException` 或 `FormatException` 原样抛给调用方）：.NET 参考实现经 AWS SDK for .NET 4.0 读取，整读（`GetObject` 不带范围）的应答里 `ETag` 不为空、不含 `-`、没有 SSE-C 与 SSE-KMS 的应答头、桶不是目录桶（S3 Express One Zone）时，SDK 把去掉两端引号的 `ETag` 当作内容的 MD5，先按十六进制解码，读内容时再核对。解不了的（去掉引号之后为空，如只有引号的 `""`；字符数为奇数；含十六进制数字之外的字符）SDK 在交出应答之前就抛出，Provider 返回 `OBJECTSTORAGE_UNAVAILABLE_001`，`reason` 写明是整读的应答里 `ETag` 不是十六进制，不带应答里的值，不重发。前两种 SDK 抛 `ArgumentOutOfRangeException`（参数名 `hex`），第三种抛 `FormatException`，与上一条解析不了的应答是同一类，`reason` 同时点名两者（2026-11-27 修订，ADR-0322；以前按异常调用栈里 SDK 解码 `ETag` 的那一帧识别，关掉栈追踪的运行时——如裁剪掉栈追踪的 Native AOT——就认不出）。范围读取、`Head`、列举与写入没有这一核对（AWS SDK for .NET 4.0 写入时不拿 `ETag` 核对内容，ADR-0317 实测），不是十六进制的 `ETag` 照常交出：`ETag` 在契约里是不透明的，Provider 不另加十六进制的要求。
  - 整读的内容对不上 `ETag`（2026-11-27 写明，ADR-0322；以前读内容的流原样抛出 SDK 的 `AmazonClientException`）：`ETag` 解得了而不是内容的 MD5 时（兼容服务给单次写入的对象的 `ETag` 不是 MD5，又没有 SSE 的应答头），SDK 读到内容末尾才发现，这时元数据已经交出、内容已经读出。读内容的流只能以异常报告，于是抛出携带 `OBJECTSTORAGE_UNAVAILABLE_001` 的异常（.NET 是 `FrameworkException`，`Code` 为该码，消息是固定的英文，不带应答里的值），不再抛 SDK 自己的异常；调用方要丢弃已经读到的字节。SDK 读内容时做的其余核对（应答里的校验和头）对不上同此。只在读到内容的末尾时报告（2026-11-27 写明，ADR-0333；以前正文没有写释放的情形，.NET 在调用方读够了声明的长度、没读到末尾就释放流时，释放也抛出这个异常）：AWS SDK for .NET 4.0 在返回 0 的那次读（内容的末尾）核对，释放时也核对——已读的字节数等于应答声明的长度就算，核对过一次不再核对。Provider 在它交出的流上判断是否读到了末尾：有一次请求了至少一个字节的读返回 0。读到末尾的，核对失败在那次读里抛出（同上），之后的释放不再抛出；没读到末尾就释放的，释放不抛出（释放不抛出是 .NET 的约定），只记一条 Warning。所以要得到这个报告，调用方要读到返回 0（`ReadToEnd`、`CopyTo` 都会读到）；只读声明的长度（`ReadExactly`）就释放的拿不到。
  - 本来就没有的不算缺：写入结果的修改时间取本机收到 `PutObject` 应答时的时钟（见「契约」），不为它另发 `Head`——多一个请求，写入成功之后 `Head` 失败会把成功报成失败，并发覆盖时还可能读到别人写的那一版。
  - 完成分片上传的应答只有 `ETag`（在响应体里），Provider 不用它：完成之后再 `Head` 一次取长度、内容类型、自定义元数据与修改时间，按 `HeadObject` 判定；这次 `Head` 缺内容时返回 `OBJECTSTORAGE_UNAVAILABLE_001`，而对象已经拼成。
  - 只判存在与否的 `Head`（批量删除之前，不覆盖的写入、分片上传的发起与完成之前）与范围读取起点越界时为取总长而发的 `Head` 不用 `ETag` 与修改时间，不因缺了它们失败；前者也不用长度，后者只用长度（见上「长度」）。
  - Provider 不用 `CopyObject`。
- 不存在的键与桶 → `OBJECTSTORAGE_NOTFOUND_001`；桶不存在的列举是空页；其余服务端错误、网络错误与 SDK 超时 → `OBJECTSTORAGE_UNAVAILABLE_001`，`reason` 同样只写异常类型的全名（2026-11-04，ADR-0115）；写入与分片上传的发起被服务以 `MetadataTooLarge` 拒收 → `OBJECTSTORAGE_VALIDATION_008`（2026-11-27 写明，ADR-0343；以前同其余服务端错误，见上「自定义元数据的值」）；服务应答成功却缺了必需的内容同样是服务端错误（2026-11-25 写明，ADR-0302；分片上传的发起、上传分片与列出分片见下文「范围读取、分片上传与预签名」，后两者 2026-11-26 写明，ADR-0308；读取、`Head`、写入、列举与批量删除见本节上文，条件写入探测见下文「S3 的条件写入探测」，2026-11-26 写明，ADR-0313；整读的 `ETag` 不是十六进制见本节上文，同日写明，ADR-0317；读取、`Head` 与列举缺长度，SDK 解析不了的应答，整读的内容对不上 `ETag` 见本节上文，列出分片里重复的编号见下文「范围读取、分片上传与预签名」，条件写入探测里上传分片缺 `ETag` 见下文「S3 的条件写入探测」，2026-11-27 写明，ADR-0322）；批量删除里单个键的失败只写 S3 的错误码。没有配额（由桶策略管理）。`EnsureBuckets` 开启时写入（含分片上传的发起）遇到桶不存在就建桶再重试一次，建桶失败同其余服务端错误（2026-11-27 写明，ADR-0333；以前 .NET 在分片上传的发起时建桶失败，SDK 的异常原样抛给调用方），默认由基础设施预先建桶。

- 客户端的设置（2026-11-24 增补，ADR-0281；以前临时凭据、超时、重试与代理只能靠应用向容器注册自己的 `IAmazonS3`，命名实例无从设置）：配置节与命名实例的设置里都有，公开面不出现 SDK 的类型；都不写时建出的客户端与以前相同。

  - `MaxAttempts`：一次操作最多发出的请求数，含首次；1 到 10（`S3ObjectStorageOptions.MaxAttemptsLimit`），1 即不重试。SDK 判定连接池里的连接已被对端关闭后重发的请求不计入（那是连接池的补救，不是对端失败后的重试）。不写时取 SDK 的缺省（标准重试模式，共 3 次）。
  - `ProxyHost`、`ProxyPort`、`ProxyUserName`、`ProxyPassword`：经 HTTP 代理访问服务。主机是主机名或 IP 字面量，不带协议、端口、路径与用户信息，带区域标识的 IPv6 地址（`fe80::1%eth0`）也不收；端口 1 到 65535；两项必须同时给出。用户名与口令可选，必须同时给出，且只能与主机、端口一起给。只给了一部分是配置错误。
  - 配置错误的处置同 `HealthBucket`：缺省实例装配失败（`ArgumentException`），命名实例 → `OBJECTSTORAGE_VALIDATION_003`。消息里只写键名与问题，带出的原值只限数值与布尔值；会话令牌、代理主机、用户名与口令的值从不进消息，服务端点（`ServiceUrl` 与绑定的主值）不合法时（含带了用户信息的，ADR-0302）同样只报键名（2026-11-25 修订，ADR-0294；以前端点的原值写进消息，写成带用户信息的地址时口令进了异常与日志）。
  - `SessionToken`、`ProxyUserName`、`ProxyPassword` 是凭据，打印选项时遮蔽（RFC-0014「选项里的凭据」）。

## S3 的条件写入探测（2026-11-01 增补，ADR-0089；同日修订，ADR-0090；2026-11-02 修订，ADR-0093）

不覆盖写入在 S3 上靠条件写入（`If-None-Match: *`）保证原子；不认它的兼容服务把条件头当作没有，先 `Head` 再写的两个写入方都会成功、后写的静默覆盖先写的（ADR-0089 实测：Garage、Zenko CloudServer 上 8 个并发的不覆盖写入全部"成功"）。S3 Provider 因此在不覆盖写入之前探明服务是否认条件写入：

- 设置 `ConditionalWrites`（配置节与命名实例的设置里都有，缺省 `true`）。开启时探测，`HealthBucket` 必须配置（探测写在这个桶里），没配是配置错误：缺省实例装配失败（`ArgumentException`），命名实例 → `OBJECTSTORAGE_VALIDATION_003`。
- 探测：对固定的探测键 `.xihan/probe/conditional-write`（保留前缀 `.xihan` 下，见「标识」，业务列举不会出现；空对象）带 `If-None-Match: *` 写入；成功则再写一次，第二次必须被拒（412），还成功就是不认。提供分片上传时（缺省实例被选为 `objectstorage.multipart`；命名实例总是提供）再以同一个键发起分片上传、上传一片、带 `If-None-Match: *` 完成，必须被拒（412），被拒的上传随即放弃；完成了就是不认（探测键被同样为空的内容覆盖，无害）。单次探测以 `HealthProbeIntervalSeconds`（缺省 15 秒，命名实例取缺省值）为超时，按注入的时钟计时。
- 探测键写入后不删除：任何一次 412 都证明服务认得条件写入，键已存在时第一次写入就被拒，所以多个实例同时启动、反复启动、后台重试都得到同一结论，没有"删掉后别人又写入"的竞态；凭据只需要对这一个键的写入（`s3:PutObject`）与放弃分片上传（`s3:AbortMultipartUpload`）的权限，不需要删除、读取或列举；桶里只多一个空对象，在保留前缀下，业务列举跳过它。`EnsureBuckets` 开启时探测桶不存在就建桶后重试一次（同写入）。
- 一次探测的结论：通过（"已确认"）；探明不认（第二次写入或完成没被拒，或服务回 501，`OBJECTSTORAGE_UNAVAILABLE_003`）；其余都是"尚未确认"（服务认不认条件写入还不知道），按原因分两类——配置错误：凭据无效或无权写探测键、建桶、放弃上传（403，`OBJECTSTORAGE_DENIED_002`，参数 `bucket`、`key`、`operation`、`reason` 为服务端错误码）、探测桶不存在（`OBJECTSTORAGE_NOTFOUND_001`，参数 `bucket`）；连不上：连不上、超时或其余服务端错误（`OBJECTSTORAGE_UNAVAILABLE_001`，`reason` 带出是哪一步）；服务的应答不合规同此（2026-11-26 写明，ADR-0313；以前拿着发起分片上传的应答里缺失或当不了句柄的上传标识照样发上传分片，报成上传分片那一步的服务端错误）：发起分片上传的应答没有可用的上传标识（判定同「范围读取、分片上传与预签名」），`reason` 写明是发起这一步的应答缺了上传标识、不带应答里的值，不再发上传分片，这个上传也放弃不了（没有标识），留给桶的生命周期规则清理；这种应答的重试单独退避、设次数上限，见下文「发起分片上传的应答缺上传标识时的重试」。上传分片的应答没有可用的 `ETag`（判定同「范围读取、分片上传与预签名」）同此（2026-11-27 写明，ADR-0322；以前拿空的 `ETag` 照样发带条件的完成，结论取决于服务先判条件还是先判分片：先判分片的回 `InvalidPart`，报成完成那一步的服务端错误）：`reason` 写明是上传分片这一步的应答缺了 `ETag`、不带应答里的值，不发完成，尽力放弃这个上传（有上传标识，放弃得了；放弃失败留给生命周期规则），按上一条与其余服务端错误同一节奏重试，不计入缺上传标识的次数。它与其余服务端错误一样不说明服务认不认条件写入，所以不是不认；也不是要改凭据或建桶的配置错误。已确认与不认是终态，服务的能力不会在运行中改变；尚未确认会重试。
- 时机：缺省实例在特性启动时探一次，与健康项的首次探测并行（S3 连不上时两者都要等到超时，并行让启动只等一个超时）；命名实例在建出时探一次（每个实例各探各的，实例指向的服务可能不同）。
- 启动或建实例时的结论（2026-11-02 修订，ADR-0093）：探明不认、被拒绝、探测桶不存在都是配置问题，要早暴露 → 缺省实例以 `KERNEL_HOSTING_002`（内层分别为 `OBJECTSTORAGE_UNAVAILABLE_003`、`OBJECTSTORAGE_DENIED_002`、`OBJECTSTORAGE_NOTFOUND_001`，参数同上）启动失败；命名实例不建、不登记（Provider 抛出携带该码的 `FrameworkException`，注册表原样返回该码，下次取用重新探测）。只有连不上（`OBJECTSTORAGE_UNAVAILABLE_001`，含服务的应答不合规，ADR-0313）→ 照常启动、照常建出并登记实例，在后台重试：第一次 1 秒后，之后每次间隔加倍，最长 `HealthProbeIntervalSeconds`（它小于 1 秒时每次都取它），计时用注入的时钟（发起分片上传的应答缺上传标识时按下一条退避，ADR-0317）；有了终态即停止，应用停止或实例释放时也停止；S3 修好（服务就绪、网络恢复）后自动确认，不必重启。`EnsureBuckets` 开启时缺桶先建（同写入），建桶被拒仍是被拒绝。`S3BlobStore` 没有公开构造，公开面不出现 SDK 的类型（2026-11-24 修订，ADR-0266）：缺省实例由特性建出，命名实例由 Provider 建出，都按本节探测。
- 发起分片上传的应答缺上传标识时的重试（2026-11-26 修订，ADR-0317；以前与连不上同一节奏：后台第一次 1 秒后、加倍到 `HealthProbeIntervalSeconds`、不设次数上限，写入距上一次探测满 1 秒即就地探测，服务若确实建了上传，每次重试都留下一个放弃不了的上传，写入密集时至多每秒一个）：这种应答说明服务可能已经建了上传，而探测没有标识、放弃不了它，重试多少次就可能留下多少个，所以单独退避并设次数上限，让留下的上传有界。
  - 计数：每次探测的发起拿到这种应答，连续次数 `n` 与累计次数各记一次。发起的应答带着可用的上传标识时连续次数清零，回到上一条的节奏（间隔照它接着加倍）；累计次数不清零，中间夹着正常的应答也照样累计（只按连续计，时好时坏的应答一再清零，就到不了上限）。探测没走到发起（如写探测键时连不上）两项都不动。
  - 退避：`n` 不为 0 时，后台的下一次探测排在上一次探测结束的 `HealthProbeIntervalSeconds` × 2^(`n` − 1) 之后，最长 1 小时（`HealthProbeIntervalSeconds` 比 1 小时长时每次都取它），计时用注入的时钟；缺省 15 秒时依次是 15 秒、30 秒、1、2、4、8、16、32 分钟与 1 小时，起点就是上一条节奏的上限，不比连不上时重试得快。这期间写入不就地探测：不覆盖写入直接返回 `OBJECTSTORAGE_UNAVAILABLE_004`（`reason` 为 `OBJECTSTORAGE_UNAVAILABLE_001`），只由后台探测。
  - 上限：累计 10 次之后不再探测，后台停止，写入也不探。状态仍是尚未确认（`conditionalWrites` 为 `unconfirmed`），不覆盖写入一律 `OBJECTSTORAGE_UNAVAILABLE_004`；缺省实例的健康项 Failed（错误仍是那次的 `OBJECTSTORAGE_UNAVAILABLE_001`，不再自动恢复，要人处理，与还在重试的 Degraded 区分开），命名实例照注册表的规则 Degraded；记一条 Error 日志。修好服务或中间的代理之后重启应用（命名实例：替换定义或移除后重新登记）才再探测。按缺省间隔，这 10 次探测分布在约 2 小时里。
  - 每个实例因此至多留下 10 个放弃不了的上传，它们都没有分片（拿不到标识就不发上传分片）；重启应用或重新建实例重新计数。探测桶要配放弃未完成分片上传的生命周期规则（Amazon S3 的 `AbortIncompleteMultipartUpload`，兼容服务按各自的等价规则），否则这些上传一直留着。
- 尚未确认时的不覆盖写入（`Overwrite = false` 的写入、分片上传的发起与完成）：有探测正在进行就等它的结论（受调用方取消约束）；没有而距上一次探测结束已满 1 秒，就地探测一次（同一时刻每个实例只有一个探测，后台重试与写入共用它）；不满 1 秒不再探测，发起分片上传的应答缺上传标识的连续次数不为 0 时，或已因它不再探测时，也不就地探测（见上一条，ADR-0317）。之后已确认就照常写入；不认 → `OBJECTSTORAGE_UNAVAILABLE_003`；仍未确认 → `OBJECTSTORAGE_UNAVAILABLE_004`（HTTP 503，参数 `container`、`key`、`reason` 为最近一次探测失败的错误码），不访问写入目标，不退回先查再写。覆盖写入、读取、删除、列举、预签名不受影响。
- 启动之后（后台重试或写入时的探测）才探明不认：应用不停止（已经在服务），此后不覆盖写入一律 `OBJECTSTORAGE_UNAVAILABLE_003`，记一条 Error 日志；换成认条件写入的服务，或关闭条件写入后重启才恢复。
- 启动之后才遇到被拒绝或探测桶不存在（2026-11-02 增补，ADR-0093；只会发生在启动或建实例时连不上、尚未确认的实例上，例如连上时凭据已被吊销、桶已被删除，或配置本来就错而启动时探不到）：应用不停止，状态仍是尚未确认，后台照常按退避重试，权限改好或桶建好后自动确认、不必重启；不覆盖写入仍是 `OBJECTSTORAGE_UNAVAILABLE_004`（HTTP 503，`reason` 为 `OBJECTSTORAGE_DENIED_002` 或 `OBJECTSTORAGE_NOTFOUND_001`），不访问写入目标——这次写入的调用方没有过错，不以 403 / 404 回给它；缺省实例的健康项 Failed（配置错误要人处理，与连不上的 Degraded 区分开），错误为该码；原因变化时记一条 Error 日志（连不上是 Warning），稳定的失败不随每次重试刷屏。已定（2026-11-02，ADR-0097）：维持继续重试、缺省实例健康项 Failed，不改为停止重试（修好要重启）或只记 Degraded（看不出要人处理）；命名实例的健康项按注册表的规则一律 Degraded（RFC 下文「命名存储实例」），不为此改注册表。已确认之后凭据被吊销或桶被删除不在此列：已确认是终态、不再探测，此后的读写照常访问存储，按「S3 Provider」的错误映射失败（被拒等服务端错误 → `OBJECTSTORAGE_UNAVAILABLE_001`），连通性的 `Head` 失败使健康项 Degraded。
- 健康：缺省实例的健康项 `objectstorage.s3.connection` 合并连通性（对 `HealthBucket` 的 `Head`）与条件写入的状态，数据 `conditionalWrites` 为 `confirmed` / `unconfirmed` / `unsupported` / `disabled`：尚未确认时错误是最近一次探测失败，即便 `Head` 成功——连不上（`OBJECTSTORAGE_UNAVAILABLE_001`）为 Degraded，被拒绝或探测桶不存在（`OBJECTSTORAGE_DENIED_002` / `NOTFOUND_001`，只在启动之后才会出现）为 Failed，发起分片上传的应答累计 10 次缺上传标识、不再探测之后同样为 Failed（ADR-0317）；探明不认时 Failed，错误为 `OBJECTSTORAGE_UNAVAILABLE_003`；状态随探测结论即时变化，不等下一轮健康探测；Failed 的条目让应用的聚合状态为 Degraded，应用仍就绪。命名实例的健康项 `objectstorage.store.<name>` 在连通之后同样看条件写入：尚未确认或不认时 Degraded（注册表把探测失败一律记为 Degraded），错误同上。
- 关闭（`ConditionalWrites = false`）表示应用明确不需要不覆盖写入（只覆盖写入，或凭据只读，或服务实测不认条件写入）：不探测，`HealthBucket` 可以不配（健康项列桶），`Overwrite = false` 的写入、分片上传的发起与完成一律 → `OBJECTSTORAGE_UNAVAILABLE_003`，不访问存储——不做没有保证的先查再写；覆盖写入、读取、删除、列举、预签名不受影响。

## 范围读取、分片上传与预签名（2026-10-29 增补，ADR-0049）

分片上传的句柄 `BlobMultipartUpload(container, key, uploadId)` 的覆盖标志 `Overwrite` 是必填的初始化成员：重建句柄（从签名地址、存下的状态）时必须写明，与开始上传时一致；完成时 Provider 可能按句柄上的值决定是否条件写入（2026-11-11 修订，ADR-0163）。

大文件直传、断点续传、音视频拖动与限时下载链接（预签名下载，缺省 30 分钟）。

- 范围读取（`objectstorage.blob@1` 的一部分）：`Get(container, key, range)`，范围是起点与可选长度；长度为空读到末尾，超出末尾截断；返回的内容带实际范围（起点、长度、总长），元数据长度仍是总长。起点不在对象内（含空对象）→ `OBJECTSTORAGE_VALIDATION_001`。
- 分片上传（能力 `objectstorage.multipart@1`，`IBlobMultipartStore`）：`Start(container, key, options)` 得到上传标识（不透明）；`UploadPart(upload, n, stream)` 上传编号 1–10000 的一片，可乱序、可重传（后一次覆盖），返回该片 ETag；`ListParts(upload)` 按编号升序列出已上传的分片（续传据此跳过）；`Complete(upload, parts)` 按编号严格升序、ETag 与已上传的一致的清单拼成对象，除最后一片外每片至少 5 MiB；`Abort(uploads)` 批量丢弃（2026-11-24 修订，ADR-0266）：按入参顺序逐项执行，返回等长、同序的逐项结果；上传不存在也成功，所以同一批里重复的上传每一项都成功；空集合不访问存储、返回空；存储不可达只记在该项上（`OBJECTSTORAGE_UNAVAILABLE_001`），其余项照常；每一项之前检查取消，已放弃的不恢复；集合里有空项是编程错误，在放弃任何上传之前抛出。单条是批量的特例。完成前对象不可见；完成是原子的。
  - 清单不合法（为空、乱序、未上传或 ETag 不符、非末片过小）→ `OBJECTSTORAGE_VALIDATION_002`，上传保留可再完成；上传不存在或已结束 → `OBJECTSTORAGE_NOTFOUND_002`；`Overwrite = false` 时对象已存在，发起与完成都 → `OBJECTSTORAGE_CONFLICT_001`。
- 预签名（能力 `objectstorage.presign@1`，`IBlobUrlSigner`）：签出限时地址，客户端不带凭据直接下载（`GET`，支持 `Range`，可带保存的文件名）、上传整个对象（`PUT`，可限定内容类型）或上传分片上传的某一片（`PUT`，响应 `ETag` 即分片 ETag）。有效期缺省 30 分钟，1 秒到 7 天。签出的地址带客户端必须发送的请求头。签名是本地计算，不检查对象是否存在。限定的内容类型须满足内容类型文法（`BlobPutOptions.IsValidContentType`），保存的文件名不为空、不全是空白（RFC-0001「空白字符」）、不含控制字符与孤立的代理项（「标识」，2026-11-26 修订，ADR-0316）、按 UTF-8 编码后不超过 255 字节（`BlobUrlRequest.MaxDownloadFileNameBytes`；2026-11-24 写明单位，ADR-0282：以前写「1 到 255 个字符」，没有说按什么计，.NET 按 UTF-16 码元计；全是空白的文件名 .NET 一向拒绝，正文没有写），不合法在构造 `BlobUrlRequest` 时抛出 `ArgumentException`（2026-11-13 修订，ADR-0219；以前只要求不空白：宿主签名的规范串以换行分隔各限定项，值里带换行就能把一项挪成另一项，S3 的响应头覆盖也会把换行写进头）。
  - 原生支持的存储（S3）由存储签名、客户端直连存储。
  - 不支持的存储（文件系统）由宿主代收发：地址指向宿主的端点，签名是对方法、容器、键、过期时刻与各限定项的 HMAC-SHA256，无状态，同一密钥的多个实例互认。规范串严格编码成 UTF-8 再计算（2026-11-26 写明，ADR-0316；以前 .NET 宽松编码，孤立的代理项换成 U+FFFD 再签）：签进去的各项要么是合文法的标识（不含孤立的代理项，见「标识」），要么是宿主从 UTF-8 字节解码出的路径与查询串，编码不成说明有值绕过了文法的核对，签名与验签都按编程错误抛出，不换成 U+FFFD 之后照算。端点验签后经存储收发，签名不符或过期 → `OBJECTSTORAGE_DENIED_001`（HTTP 403），范围不可满足回 416。上传的签名没有限定内容类型时对象的内容类型取请求的 `Content-Type`，不合内容类型文法 → `OBJECTSTORAGE_VALIDATION_006`（HTTP 400），不写入（2026-11-13 修订，ADR-0214）。端点照 RFC 9110 §5.5 先去掉 `Content-Type` 首尾的空白（OWS，即空格与制表符）再用它，各宿主结果一致（2026-11-26 写明，ADR-0314；以前端点原样使用宿主交来的值，Kestrel 交给应用之前已经去掉首尾的空白，进程内的测试服务器原样转交，同一个以空格结尾的 `Content-Type` 经 Kestrel 照存、经测试服务器回 400）：签名限定了内容类型时以去掉之后的值与它比较（不区分大小写，不同即 `OBJECTSTORAGE_DENIED_001`）；没限定时去掉之后为空即当作没给，对象的内容类型取缺省的 `application/octet-stream`，否则以去掉之后的值核对文法、写入。只去空格与制表符：别的空白（不换行空格、控制字符）不是 HTTP 的空白，留在值里，不合文法照样回 400（以前 .NET 按 `string.IsNullOrWhiteSpace` 判空，只有这类空白的值当作没给）。端点读的请求头只有上传的 `Content-Type` 与下载的 `Range`；`Range` 经宿主的头解析器，本来就去掉首尾的空白；签名的各项在地址的查询串里，不是请求头。端点的响应都带 `X-Content-Type-Options: nosniff`；写出内容时带 `Content-Security-Policy: sandbox; default-src 'none'; img-src 'self' data:; media-src 'self'; style-src 'unsafe-inline'`，PDF 除外，应用已经设了这个头时不覆盖（2026-11-04 修订，ADR-0125）。
- 文件系统：范围读取定位后只交出该段；分片暂存在容器的 `uploads/<上传标识>/`，分片文件名带内容的 SHA-256，完成时拼接成同目录临时文件再原子替换并计入配额；单片与拼接后的对象受单对象上限约束。暂存有界（2026-11-12 修订，ADR-0184；以前暂存的分片不计入配额、上传数不限、过期的上传只在启动时清掉且清掉之前照样能传分片）：暂存的分片边写边预留、计入总配额，完成或放弃后扣除；未完成的上传数不超过 `MaxMultipartUploads`（默认 1000），满了发起即 `OBJECTSTORAGE_UNAVAILABLE_002`（消息键 `objectstorage.multipart.uploads_exhausted`，参数 `limit`）；超过 `MultipartExpiry`（默认 7 天）未完成的上传当作不存在（再传分片、列举与完成都是 `OBJECTSTORAGE_NOTFOUND_002`），碰到即清掉，启动扫描时与运行期间发起新上传时（至多每小时一次）也清掉。
- S3：范围读取经 `Range` 头；分片直接映射 S3 multipart（不覆盖的完成先 `Head` 再带 `If-None-Match: *`，服务认条件完成要先由探测确认：尚未确认时不覆盖的发起与完成 → `OBJECTSTORAGE_UNAVAILABLE_004`，探明不认或关闭条件写入时 → `OBJECTSTORAGE_UNAVAILABLE_003`）；预签名经 SDK（签名 V4），兼容服务的端点是 http 时按 http 签。
  - 发起的应答没有可用的上传标识（2026-11-25 写明，ADR-0302；以前 .NET 把应答里的标识直接交给句柄的构造，没有标识时抛出 `ArgumentNullException`，为空或当不了句柄时抛出 `ArgumentException`）：服务回了成功，应答里却没有上传标识、标识为空，或当不了句柄（.NET 的 `BlobMultipartUpload` 要求 1 到 1024 个字符、不含空白、控制字符与孤立的代理项，后一项 2026-11-26 起，ADR-0316），是不合规的应答，按「S3 Provider」的映射同其余服务端错误：返回 `OBJECTSTORAGE_UNAVAILABLE_001`，不抛出；`reason` 写明是发起的应答没有可用的上传标识，不带应答里的值。不重发：服务端可能已经建了这个上传，没有标识就放弃不了，由桶的生命周期规则（未完成的分片上传过期即放弃）清理。
  - 上传分片与列出分片的应答缺必需的内容（2026-11-26 写明，ADR-0308；以前 .NET 把应答里的值直接交给分片 `BlobPart` 的构造：上传分片的应答没有 `ETag` 时抛出 `ArgumentException`，列出的分片没有编号时按 0 交给编号的核对、抛出 `ArgumentOutOfRangeException`）：同发起一样是不合规的应答，返回 `OBJECTSTORAGE_UNAVAILABLE_001`，不抛出；`reason` 写明是哪一步的应答缺了什么，不带应答里的值。
    - 上传分片的应答没有可用的 `ETag`：缺失、为空，或去掉两端的引号之后为空或只有空白（RFC-0001「空白字符」）。不重发：分片可能已在服务端，调用方可以重传同一编号（后一次覆盖），或从列出分片里取它的 `ETag`。
    - 列出分片的应答里有一个分片没有可用的编号（缺失，或不在 1–10000 之内）、没有可用的 `ETag`（同上），或长度为负：整个列出失败，不跳过那个分片——跳过之后的清单会让续传重传它，或让完成清单少一片。分片的长度缺失照旧当作 0：它只用于说明，完成时不核对。
    - 列出分片的分页不前进（2026-11-26 写明，ADR-0313；以前 .NET 在应答说截断了却不给续页标记时从头重新请求，循环不止、列表一直增长，直到调用方取消）：应答说截断了（`IsTruncated`），续页标记 `NextPartNumberMarker`（S3 写明它是这一页的最后一片）却缺失、不比这一页请求的起点（`PartNumberMarker`，第一页为 0）大，或不小于 10000——截断说明后面还有编号更大的分片，而编号最大是 10000。同一编号出现两次（同一页里，或这一页与前面的页之间）同样不合规（2026-11-27 修订，ADR-0322；以前只在累计列出的分片超过 10000 个时失败，10000 片之内重复的编号原样交出，调用方拿它去完成，清单不是严格升序，得到 `OBJECTSTORAGE_VALIDATION_002`，像是自己给错了清单）：一个上传的每个编号至多一片，后一次上传覆盖前一次。这一页交出的分片编号不比这一页请求的起点大（S3 的 `ListParts` 只交出编号大于 `PartNumberMarker` 的分片）同样不合规（2026-11-27 写明，ADR-0333；以前只要不重复就照收，交出的清单里混进了起点之前的分片）；同一编号重复又不比起点大的，按重复报告。都整个列出失败，不交出已列出的部分。续页标记因此每页严格增大且小于 10000，一次列出至多请求 10000 页；编号在 1–10000 之内且各不相同，至多 10000 片，不再另数片数。

## 命名存储实例（2026-10-29 增补，ADR-0050）

一个应用同时用多个存储：按租户或按用途各配一个桶、各有自己的端点与密钥，定义可以写在配置里，也可以在运行时来自应用自己的库。

- 定义 `BlobStoreDefinition`：实例名（`^[a-z0-9][a-z0-9-]{0,63}$`）、Provider 名（`filesystem`、`s3`，不区分大小写）与设置。设置的键同该 Provider 的配置节，不区分大小写；未知的键是错误，拼错的键不会被静默忽略。
- Provider `IBlobStoreProvider`：每个存储包一个，按定义建实例、探测实例。`CreateAsync` 返回 `Result<IBlobStore>`，失败不抛出（2026-11-11 修订，ADR-0150）：设置不合法 → `OBJECTSTORAGE_VALIDATION_003`，后端此刻建不出来 → `OBJECTSTORAGE_UNAVAILABLE_001`（`BlobStoreFailures` 给出标准错误，原因只写异常类型、完整异常由 Provider 记日志），探测发现不能用 → 探测的错误码；失败时 Provider 自己释放已建的资源。文件系统的命名实例必须给 `RootPath`（不给就会与缺省实例落在同一目录）；S3 的命名实例各建各的客户端，不读连接绑定，探测间隔不在设置里；`ConditionalWrites` 开启（缺省）时建实例时探测条件写入，探明不认、被拒绝或探测桶不存在都不建，只有连不上的照常建出、在后台重试（「S3 的条件写入探测」）。
- 命名实例的端点可能来自应用的库，不可信（2026-11-04 修订，ADR-0117）：S3 命名实例的客户端过出站地址策略（RFC-0008），自建存储的地址要放行；被拒绝与连不上同样处理，建实例时的探测只算尚未确认，读写返回 `OBJECTSTORAGE_UNAVAILABLE_001`。缺省实例的端点是运维配的，不过策略。命名实例配了代理时（2026-11-24 增补，ADR-0281），本进程连的是代理：过策略的是代理的地址，被拒绝与连不上同样处理；端点由代理去解析、去连，本进程的策略管不到，要限制经代理能到的目标就在代理上做。命名实例的设置里配代理（`ProxyHost` 等四项）只在运营方打开 `XiHan:ObjectStorage:S3:NamedInstancesAllowProxy` 时允许（2026-11-25 修订，ADR-0294；以前与缺省实例一样总能配）：开关缺省 `false`，不是布尔值时建 Provider 即失败；没打开而定义配了代理是 `OBJECTSTORAGE_VALIDATION_003`，原因不带代理的任何取值；打开之后照上面的规则过策略。策略放行了一个内网正向代理的部署里，能填实例设置的人就能经它到达策略本来拒绝的地址，所以这一步由运营方决定。缺省实例的代理是运营方自己配的，不受这个开关约束。S3 命名实例必须给出 `AccessKey` 与 `SecretKey`（2026-11-12 修订，ADR-0178）：设置可以由租户填写，没给密钥就会用宿主的 AWS 凭据链（环境变量、配置文件、实例角色），等于把宿主的身份借给填设置的人；只给一项总是 `OBJECTSTORAGE_VALIDATION_003`，两项都不给只在运营方打开 `XiHan:ObjectStorage:S3:NamedInstancesUseAmbientCredentials` 时允许。这两个运营方开关都在配置节 `XiHan:ObjectStorage:S3` 下，不在实例设置的键里，不能经实例设置打开。缺省实例两项都空时走凭据链，只给一项同样是配置错误（「S3 Provider」，ADR-0294）。
- 登记规则（2026-11-01 修订，ADR-0075）：存储包只要装配（`UseFeature`）就登记自己的命名实例 Provider，与它是否被选为缺省实例无关。能力全部被别的存储顶替的存储包实现 `IShadowAwareFeature`（RFC-0002 解析规则 4），被顶替时只登记命名实例 Provider：不读自己的配置节与连接绑定、不建缺省实例、不启动。
- 注册表 `BlobStores`（单例；装配任一个存储包即有）：
  - `Get(name)`：已建的直接返回；配置节 `XiHan:ObjectStorage:Stores:<name>`（`Provider` 加设置）里有定义的首次取用时建出；都没有 → `OBJECTSTORAGE_NOTFOUND_003`。
  - `GetOrAdd(definition)`：同名同定义（Provider 名与设置完全相同）返回同一实例；定义变了建新实例替换并释放旧的，替换时仍在旧实例上的调用可能失败。Provider 未登记或设置不合法 → `OBJECTSTORAGE_VALIDATION_003`，后端此刻建不出来（目录无权限、磁盘错误）→ `OBJECTSTORAGE_UNAVAILABLE_001`，登记已满 → `OBJECTSTORAGE_UNAVAILABLE_005`（见下面「容量」），建实例时的探测发现实例不能用 → Provider 给出的错误码（Provider 抛出携带错误码的 `FrameworkException`，注册表转成同码的失败结果；S3 在探明不认条件写入、探测被拒绝或探测桶不存在时如此，连不上的照常建出，见「S3 的条件写入探测」）；这些情况已有的同名实例都不受影响。
  - `Remove(names)` 批量移除并释放（2026-11-24 修订，ADR-0266）：逐项返回是否存在过，与入参同序，同一批里重复的名字第二次为否，空集合返回空；整批一次加锁移除，某个实例释放失败只记日志，不影响其余实例与返回值。应用停止时释放全部。
  - 容量（2026-11-24 修订，ADR-0266）：已建的实例数上限 `XiHan:ObjectStorage:StoreMaxCount`（缺省 64，1–1024；配置定义与运行时登记的都算）。满了再登记新名字（含首次取用配置定义的实例）→ `OBJECTSTORAGE_UNAVAILABLE_005`，不建实例、不淘汰已有的；替换同名的不占名额，移除腾出名额。
  - 缺省的 `IBlobStore` 注入方式不变，命名实例与缺省实例互不相干。
- 缺省实例的三个契约落在同一存储上（2026-11-01 修订，ADR-0075；同日再修订，ADR-0082：只约束被要求的契约）。存储包在 `Configure` 开头按自己被选中的能力判定（`BlobStoreSelection.ProvidesDefaultInstance`）：
  - 被选为 `objectstorage.blob`：它就是缺省存储，照常为被选中的各项能力注册契约（兜底选出的也注册）。
  - 没被选为 `objectstorage.blob`，却被要求提供 `objectstorage.multipart` 或 `objectstorage.presign`（RFC-0002 解析规则 4：有清单依赖这项能力，或 `XiHan:Providers:<能力ID>` / `UseProvider` 指定了它）：缺省存储是别的存储，它签出的地址、建的分片上传会指向另一个存储里的对象，装配时抛出携带 `OBJECTSTORAGE_VALIDATION_004` 的 `FrameworkException`，应用启动失败，消息列出被要求的能力与要改的 `XiHan:Providers` 键；框架不替应用改选。
  - 没被选为 `objectstorage.blob`，分片上传与预签名也都只是兜底选出（没人依赖、没人指定）：它不提供缺省实例，按被顶替处理（`ConfigureShadowed`：只登记命名实例 Provider，不读配置节与连接绑定、不建缺省实例、不注册这两个契约、不启动）。这时容器里没有缺省的 `IBlobMultipartStore` / `IBlobUrlSigner`，要用就在清单里依赖对应能力或指定 Provider，由上一条核对。
  - 宿主代收发（`xihan.hosting.blob-urls`）经缺省 `IBlobStore` 收发，不是存储包，不受此约束。
  - 混装文件系统与 S3、以文件系统为缺省实例：只指定 `objectstorage.blob` = `xihan.objectstorage.filesystem` 即可，S3 的分片上传与预签名是兜底选出，S3 只登记命名实例，不必装 `HostedBlobUrlFeature`；要缺省的分片上传，再指定 `objectstorage.multipart` = `xihan.objectstorage.filesystem`；要缺省的预签名，装配 `HostedBlobUrlFeature` 并指定 `objectstorage.presign` = `xihan.hosting.blob-urls`（S3 与它都是显式 Provider，不指定本来就是 `KERNEL_CAPABILITY_004`）。有特性依赖 `objectstorage.presign` 或 `objectstorage.multipart`（例如应用的文件模块）而没指定时，这项能力解析到 S3 且是被要求的，仍然 `OBJECTSTORAGE_VALIDATION_004`。都不指定时 S3 是显式 Provider，三项都归 S3，文件系统被顶替。
- 命名实例的能力随实例本身：S3 实例同时是 `IBlobMultipartStore` 与 `IBlobUrlSigner`（直连存储）；文件系统实例实现分片，预签名由宿主代收发——宿主签名器的 `ForStore(name)` 签出的地址带 `x-store=<name>`，实例名在签名里（改成别的实例或去掉即签名不符），端点经注册表取实例；签名有效但实例不存在 → `OBJECTSTORAGE_NOTFOUND_003`（HTTP 404）。
- 健康：每个实例一条 `objectstorage.store.<name>`，按 `XiHan:ObjectStorage:StoreHealthProbeIntervalSeconds`（缺省 15 秒）在后台逐个探测，新实例建出后立即探一次；尚未探过为 Started，探测失败为 Degraded（实例仍可取用）。文件系统看总配额是否还有余量，S3 对实例的 `HealthBucket` 做 `Head`（没配时列桶），连通之后再看条件写入是否已确认（「S3 的条件写入探测」）。条目名随实例而定，存储包的清单不列出它们。

## 一致性

Provider 必须继承 `BlobStoreConformance` 并通过全部用例（S3 Provider 对 RustFS 通过，此前对 MinIO 通过；ADR-0086 记录了其余兼容服务的差异）。用例包括并发的不覆盖写入（8 个写入方同时写同一个新键，恰好一个成功，ADR-0089）：先查再写的实现过不了，不认条件写入的 S3 兼容服务上不经探测建的 `S3BlobStore`（参考实现的测试经内部构造）也过不了（Garage、Zenko CloudServer 上 8 个全部成功），这正是 S3 Provider 探明之前不做不覆盖写入、探明不认就拒绝的原因；以及保留前缀（ADR-0090）：首段是 `.xihan` 的键构造时被拒，套件经 Provider 实现的钩子 `PlantOutsideContractAsync` 绕过契约在存储里放入保留前缀下的对象，列举必须跳过它们；以及内容类型原样存取（2026-11-25 增补，ADR-0295）：空参数、`;` 两侧的空格与引号里的 `;` 写入、读出与把读出的值写回都不变，写不出原值的返回 `OBJECTSTORAGE_VALIDATION_007` 且不写入，分片上传的发起同此；实现了 `IBlobMultipartStore` 的 Provider 同样要通过分片用例，含批量放弃（不实现时这些用例跳过）。命名实例的 Provider 必须继承 `BlobStoreProviderConformance` 并通过全部用例（参考实现另有混装用例：两种装配顺序下两个存储包的命名实例 Provider 都登记，缺省的三个契约同一存储，被要求的契约选得不一致时装配失败、兜底选出的不失败而按被顶替处理）：按定义建出可读写且探测通过的实例、未知的设置键被拒绝、经注册表同定义复用 / 定义变了替换 / 批量移除逐项报告、移除后不存在、定义错误翻译为 `OBJECTSTORAGE_VALIDATION_003` 且不影响已有实例。

向量（档 `objectstorage`，`conformance/vectors/objectstorage/`；2026-11-24，ADR-0277，以前这个档没有向量；同日 ADR-0282 补上长度按字节计、查询前缀、保存的文件名与内容类型的参数；2026-11-25 ADR-0295 把 `;` 之后为空的写法挪到合法一侧；2026-11-26 ADR-0308 把以空格结尾的写法挪到不合法一侧；同日 ADR-0316 给键、查询前缀与保存的文件名补上孤立的代理项与成对的代理项；2026-11-27 ADR-0322 给元数据的值补上同样的用例）。JSON 字符串写不出孤立的代理项（各语言的 JSON 读取器对转义出的孤立代理项读法不同：System.Text.Json 抛出，Go 换成 U+FFFD，Python 原样保留），这几条用例不写原文，以 `utf16` 列出 UTF-16 码元（四位十六进制），各实现按码元组出本语言的字符串：UTF-16 的语言直接组成，以字节表示字符串的语言按 WTF-8 编成字节（成对的代理项合成平面以外的字符编成 4 个字节，孤立的代理项各编成 3 个字节 `ED A0 80`–`ED BF BF`），以码位表示字符串的语言（Python）把成对的代理项合成一个码位、孤立的代理项以它的码元值作码位；同一个合法的键另以码元写出一次，核对组字符串的写法：

| 文件 | 内容 |
| --- | --- |
| `container-names.json` | 容器名文法的合法与不合法样例，含 3 与 63 个字符的两侧 |
| `blob-keys.json` | 对象键的文法（分段、`.` 与 `..`、空白、控制字符、反斜线、孤立的代理项与成对的代理项）、保留前缀与查询前缀；1024 字节的上限两侧，含码元数不超而字节数超过的，每条标出 UTF-8 字节数与 UTF-16 码元数 |
| `blob-metadata.json` | 自定义元数据名的文法，值里的控制字符、孤立的代理项与成对的代理项，名与值合计 2048 个 UTF-8 字节的上限两侧；值里有孤立代理项的以 `utf16` 按名写出码元，不标字节数 |
| `blob-content-types.json` | 内容类型文法的合法与不合法样例：`;` 两侧的空格、`;` 之后为空的各种写法（合法）、以空格结尾的写法与制表符（不合法），含 255 个字符的上限两侧，以及正好 255 个字符、只因以空格结尾而不合法的一条 |
| `blob-ranges.json` | 范围读取的实际范围与不可满足的范围 |
| `download-file-names.json` | 预签名下载地址上保存的文件名：空白、控制字符、孤立的代理项与成对的代理项，255 字节的上限两侧，含码元数不超而字节数超过的 |
| `multipart-parts.json` | 分片编号的范围、分片的最小字节数与完成清单的编号次序 |
| `store-definitions.json` | 命名存储实例名的文法、内置的 Provider 名、两个定义是不是同一个定义 |

向量不收的：空的元数据值；预签名的有效期、列举的每页条数（都只是数值范围）；宿主代签地址的签名（正文没有给出规范串）；完成清单里 ETag 与分片大小的核对、配额与并发（由 `BlobStoreConformance` 与 `BlobMultipartStoreConformance` 核对）；S3 Provider 的配置写法（服务端点、代理主机、成组的设置，2026-11-25 写明，ADR-0302）：只有 .NET 的 S3 Provider 读这些配置，由它自己的测试核对；S3 Provider 的元数据值编解码（2026-11-27 写明，ADR-0333；写入时拒收的 encoded-word 形状与原样写进头的字节同日写明，ADR-0343）：只有 .NET 的 S3 Provider 做，由它自己的测试与对 RustFS 的门控用例核对。
