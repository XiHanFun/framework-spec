# 从 4.x 迁移：`xihan migrate v4` 的修复规则

> 规范性（RFC-0020）。定义 `xihan migrate v4` 对 4.x 代码施加的每条修复规则、映射表、标记与报告格式。实现：`XiHan.Framework.Cli`。

## 1. 原则

1. **语法级重写**：工具只读单个文件的语法树（Roslyn），不加载 MSBuild 工作区，不做跨文件类型解析；判定依据是写在源码里的名字（基类名、特性名、接口名、方法签名）。
2. **可判定的就改，不可判定的留标记**：改不了或拿不准的位置插入一行注释 `// xihan-migrate(<规则>): <说明>`，说明用工具当前区域的文案（RFC-0010）；人处理完删掉标记。
3. **幂等**：对已迁移的代码再跑一遍零改动、零标记。
4. **顺序固定**：规则按编号执行；后一条规则看到的是前一条规则改过的文件。
5. **不动语义**：规则只改入口层与协议层（模块、特性、实体协议、注入标记、时钟、事务特性、动态 API、事件、本地化、包引用），业务方法体不改写；`[DynamicApi]` 以委托模式迁移，原服务类保留。
6. **报告如实**：每条规则的命中数、改动文件、标记数与标记位置写进报告；没有命中也要出现在报告里。

## 2. 命令

```text
xihan migrate v4 [--path <目录|.csproj|.slnx>] [--fixers V4-01,V4-03] [--dry-run] [--report <文件>]
```

- `--path` 默认当前目录；给 `.csproj` 时只处理该项目目录，给 `.slnx` 时处理解决方案目录。
- `--fixers` 选择规则子集，默认全部；不认识的编号报 `CLI_VALIDATION_003`，路径不存在报 `CLI_NOTFOUND_002`，版本不是 `v4` 报 `CLI_VALIDATION_002`。
- `--dry-run` 只出报告不写文件。
- `--report` 把报告以 JSON 写到文件；终端总是打印表格。
- 跳过 `bin/`、`obj/`、`.git/`、`*.g.cs`、`*.Designer.cs`。

## 3. 标记

```csharp
// xihan-migrate(V4-05): IUnitOfWorkManager 没有 5.0 对应物；每个操作默认一个工作单元，需要显式控制时注入作用域的 IUnitOfWork。
```

标记插在受影响的成员或语句之前的独立一行，作为前导注释保留原缩进；同一位置同一规则只插一次。

## 4. 规则

### V4-01 模块 → 特性

| 4.x | 5.0 |
| --- | --- |
| `class XiHanXxxModule : XiHanModule` | `sealed class XxxFeature : IFeature`（初始化 / 关闭钩子去掉空壳后还有语句则 `IHostedFeature`）；类名去掉 `XiHan` 前缀、`Module` 换 `Feature`，文件与本文件内的引用同步改名 |
| `[DependsOn(typeof(...))]` | 删除；指向 4.x 框架模块的项按 §4.1 映射成清单 `Requires`，指向应用模块的项直接删除（DI 注册顺序无关），映射不到的记报告并留标记 |
| `PreConfigureServices` / `ConfigureServices` / `PostConfigureServices(ServiceConfigurationContext context)` | 合并为 `Configure(FeatureContext context)`，按 Pre → Configure → Post 顺序拼接方法体 |
| `OnPreApplicationInitialization` / `OnApplicationInitialization` / `OnPostApplicationInitialization(ApplicationInitializationContext context)` | 合并为 `StartAsync(IServiceProvider services, CancellationToken cancellationToken)`；体内 `context.ServiceProvider` 改 `services`；含 `GetApplicationBuilder()` 的语句留标记（管道与端点的注册搬到 `Program.cs` 的 `app.UseXiHan()` 之后） |
| `OnApplicationShutdown(ApplicationShutdownContext context)` | `StopAsync(CancellationToken cancellationToken)`；体内引用 `context` 的语句留标记（没有上下文，所需服务在 `StartAsync` 里解析并存到字段） |
| `…Async` 变体 | 同名钩子先同步后异步合并；有 `async` 钩子时生成的 `StartAsync` / `StopAsync` 为 `async`，否则末尾补 `return Task.CompletedTask;`；`ConfigureServicesAsync` 并入同步的 `Configure` 并留标记（需要 `await` 的工作移到 `StartAsync`） |
| 钩子体末尾的 `return Task.CompletedTask;` | 删除 |
| `Configure<TOptions>(...)` / `PreConfigure` / `PostConfigure` 等基类便捷方法 | `context.Services.Configure<TOptions>(...)` 等 |
| `context.Services.GetConfiguration()` | `context.Configuration` |
| `SkipAutoServiceRegistration` | 删除（5.0 没有约定注册） |

生成的清单：`Id` 为命名空间小写（`XiHan.BasicApp.Saas` → `xihan.basicapp.saas`；清单文法只允许三段，去掉 `xihan` 头后第二段起用 `-` 连成第三段，`XiHan.BasicApp.Web.Core` → `xihan.basicapp.web-core`，不足两段补 `app`），`Package` 为命名空间，`Version = "1.0.0"`，`Primitives = 1`，`Kind = Capability`，`Stability = Stable`，`Requires` 总是含 `kernel.hosting@1`（能力以各包的常量引用，如 `PersistenceCapabilities.Relational`，并补对应 `using`），`Entry` 为特性类型全名。

多个钩子体各自声明的同名局部变量（如两处 `var app = context.GetApplicationBuilder();`）合并后会重名，由编译器指引人工合并；工具不改写语句。

**被删模块丢失的注册**：`[DependsOn]` 里的 4.x 框架模块删除后，它们在 `ConfigureServices` 里做的注册（`XiHanWebCoreModule` 的 `AddHttpContextAccessor`、`XiHanDistributedIdsModule` 的 `AddXiHanDistributedIds` 等）随之消失，而承接进应用的 4.x 代码仍在消费这些服务，宿主启动时 DI 校验失败。§4.1 为每个有此类注册的模块列出「承接时需要补的注册」（4.x 扩展方法名与它注册的服务）；工具在生成的 `Configure` 末尾（原钩子体之后、空一行）按模块各留一条 `// xihan-migrate(V4-01)` 标记带上清单，由人按承接代码的实际依赖补回。迁移范围内已有同名的 `IServiceCollection` 扩展方法（应用已承接该模块的代码，如自己的 `AddXiHanDistributedIds(this IServiceCollection, IConfiguration)`）且原钩子体里还没调用时，直接生成 `context.Services.AddXiHanDistributedIds(context.Configuration);`（方法有 `IConfiguration` 参数才传配置），不再进标记；原钩子体里已调用的也不再进标记。

### V4-02 实体基类 → 协议接口

| 4.x | 5.0 |
| --- | --- |
| `BasicId` | `Id`（`IEntity<TKey>`），声明与引用一并改名：属性、记录位置参数、构造函数与方法参数、字段、局部变量（`record X(long BasicId, …)` → `record X(long Id, …)`）以及全部标识符用法 |
| `CreatedTime` / `ModifiedTime` / `DeletedTime` | `CreatedAt`（`IHasCreationTime`）/ `ModifiedAt`（`IHasModificationTime`）/ `DeletedAt`（`ISoftDeletable`） |
| `RowVersion`（`long`） | `ConcurrencyStamp`（`string`，`IHasConcurrencyStamp`）；列类型随之改为字符串，留标记提醒改表 |
| `TenantId`（`long`） | `TenantId`（`string`，`IMultiTenant`）；比较与赋值处由编译器报错指引，留标记提醒改表 |
| `IsDeleted` | 不变（`ISoftDeletable`） |
| `CreatedId` / `CreatedBy` / `ModifiedId` / `ModifiedBy` / `DeletedId` / `DeletedBy` | 不变，留在应用基类 |
| `IMultiTenantEntity`、`IStrictMultiTenantEntity` | `IMultiTenant` |
| `ITraceableEntity`、`ISplitTableEntity` | 保留为应用接口（去掉对 4.x 的继承），留标记；不算改动 |
| 构造函数 `: base(basicId)` / `: base(basicId, createdId)` | 去掉初始化器，体内补 `Id = basicId;` / `CreatedId = createdId;` |

应用里继承 4.x `SugarEntity<TKey>` / `SugarCreationEntity<TKey>` / `SugarModificationEntity<TKey>` / `SugarDeletionEntity<TKey>` / `SugarFullAuditedEntity<TKey>` / `SugarAggregateRoot<TKey>`（含 `SugarMultiTenant*` 与 `*WithIdentity` 变体）的基类，改为直接实现对应协议接口并按 §4.2 展开属性；`[SugarColumn(ColumnName = …)]` 沿用 4.x 的列名（`Basic_Id`、`Created_Time`、`Tenant_Id`、`Row_Version` …），主键列的 `IsIdentity` 按原基类（`WithIdentity` 为自增）。

### V4-03 注入标记接口 → 显式注册

删除基类列表里的 `ITransientDependency` / `IScopedDependency` / `ISingletonDependency` 与 `[Dependency]`、`[ExposeServices]`；每个项目生成 `<项目末段>V4Services.cs`（`XiHan.BasicApp.Saas` → `SaasV4Services.cs`），其中 `Add<项目末段>V4Services(this IServiceCollection)` 按原生存期把类注册到它实现的每个接口（`services.AddScoped<IFoo, Foo>()`；`[ExposeServices]` 列出的优先，`[Dependency(ServiceLifetime.X)]` 的存期优先于标记接口，多个标记接口并存按 4.x 的 Transient → Singleton → Scoped 取；`IDisposable` 等非契约接口不算），没有接口的注册自身。运行结束时在同项目的特性类（V4-01 刚转出来的，或已经是 `IFeature` / `IHostedFeature` 的）`Configure(FeatureContext …)` 开头插入 `context.Services.Add<项目末段>V4Services();`（方法里已有对 `Add<项目末段>V4Services` 的调用则不重复，特性在别的命名空间时补 `using`，表达式体改成块；插入记在 V4-01 下）；项目里没有特性类才在文件第一行留标记提醒调用。泛型或不在任何项目目录下的类不进生成文件，留标记手工注册；抽象类只去掉标记、不注册也不留标记（它的具体派生类按下一段登记）。

**继承的标记**：4.x 大量仓储与应用服务自己不写标记，靠基类上的标记由约定注册器自动注册（`XiHan.Framework.Application.ApplicationServiceBase : ITransientDependency`、应用自己的 `SaasAggregateRepository<T> : …, IScopedDependency` 等）。自己没有标记、没有 `[Dependency]` 的具体类（非抽象、非静态、非泛型、在项目目录下），第一遍扫描后沿迁移范围内的基类链向上解析存期：最近的 `[Dependency]` 优先；否则收集全链的标记接口，链走出迁移范围时查「带标记的 4.x 框架基类与接口 → 存期」表（按 `framework/src` 里 `: ITransientDependency / IScopedDependency / ISingletonDependency` 的非 sealed 类与接口生成，如 `ApplicationServiceBase`、`CrudApplicationServiceBase`、`DomainService` / `IDomainService` → Transient，`IBackgroundWorker`、`UnitOfWorkManager` → Singleton，`DbInitializer`、`SettingManager` → Scoped），按 Transient → Singleton → Scoped 取；解析不到的不注册。解析到存期的类按 4.x `ExposeServicesAttribute.GetDefaultServices` 的默认规则暴露：类本身，加上类名以「接口名去掉前导 `I`」结尾的接口（泛型接口按去掉类型实参的名字比；接口取自己基类列表里的，以及范围内基类上不含该基类类型参数的），写成 `services.TryAddScoped<RoleRepository>(); services.TryAddScoped<IRoleRepository>(static sp => sp.GetRequiredService<RoleRepository>());`（`TryAdd` 让应用的显式注册优先，转发保证同一存期内同一实例，与 4.x 约定注册一致），进同一份 `<项目末段>V4Services.cs`。标了 `[DynamicApi]`（自己或基类）的服务类由 V4-06 按作用域登记，这里不重复。再跑一遍时 4.x 框架基类仍在基类列表里，生成内容与已有文件相同则不算改动。

### V4-04 `IClock` → `TimeProvider`

类型 `IClock` 改 `TimeProvider`；同一文件内由 `IClock` 声明的字段、属性、参数名上的 `.Now` 与 `.UtcNow` 改 `.GetUtcNow()`，`.Today` 改 `.GetUtcNow().Date`。

### V4-05 `[UnitOfWork]` 与 `IUnitOfWorkManager`

删除 `[UnitOfWork(...)]`（任何参数）：每个操作在 Transaction 阶段默认一个工作单元。`IUnitOfWorkManager` 的声明与 `Begin(...)` 调用留标记，不改写：显式控制用作用域的 `IUnitOfWork`，嵌套与新事务没有对应物。

**单例消费方**：4.x 允许单例持有 `IUnitOfWorkManager`（发件箱、快照提供器只读 `Current`），应用承接的管理器是作用域的，宿主 DI 校验会拒绝单例依赖作用域服务。只读 `Current`（类里没有 `Begin` 调用）且是单例的消费类——第一遍扫到的显式 `AddSingleton<T>` / `TryAddSingleton<TService, T>` / `AddHostedService<T>`（最后一个类型实参），或按 V4-03 沿基类链继承到单例存期（如 `IBackgroundWorker`）——改为注入 `ICurrentUnitOfWorkAccessor`：类里字段、属性与参数上的 `IUnitOfWorkManager`（含限定名写法）换成 `ICurrentUnitOfWorkAccessor`，补 `using`，不留标记。访问器生成在这些消费项目引用链最底层的项目（同 V4-07 的提供者规则）的 `Data/ICurrentUnitOfWorkAccessor.cs`（`IUnitOfWork? Current`）与 `Data/CurrentUnitOfWorkAccessor.cs`（从 `IInvocationAccessor.Current` 的服务作用域解析 `IUnitOfWorkManager` 并读 `Current`，没有当前调用为空；命名空间 `<项目>.Data`，已存在不覆盖），按单例进 V4-03 的注册文件。`IUnitOfWorkManager` / `IUnitOfWork` 没有 5.0 对应物，生成文件第一行留标记：`using` 要指向应用自己承接的工作单元管理器（作用域、AsyncLocal 维护当前值；迁移范围内已声明 `IUnitOfWorkManager` 接口时直接用它的命名空间），或像 BasicApp 那样改读管理器的环境值。调用了 `Begin` 的单例与非单例消费方维持原样。

### V4-06 动态 API → 操作契约（委托模式）

对标注 `[DynamicApi]`（类或基类）的服务类的每个公开实例方法生成一个操作：

- **资源**：类名去掉 `AppService` / `ApplicationService` / `Service` 后缀转 kebab-case（`AccessPolicyAppService` → `access-policy`）。
- **动词**：方法名去掉 `Async` 与资源名后转 kebab-case；`Create` / `Add` / `Insert` → `create`，`Update` / `Modify` → `update`，`Delete` / `Remove` → `delete`，`Get` 且只有一个标识参数 → `get`，`Get…List` / `Get…Page` / `Query` / `Search` / `List` / `Find` → `list`，其余按剩余部分（`UpdateAccessPolicyStatusAsync` → `update-status`）。同一资源内重复的动词加 `-2`、`-3` 后缀并留标记。
- **请求**：方法只有一个非 `CancellationToken` 参数且其类型以 `Dto` / `Request` / `Input` 结尾时直接用它；否则生成 `record <方法名>Request(<参数>…)`。
- **响应**：`Task<T>` / `ValueTask<T>` 取 `T`；`Task` / `void` 用项目生成的 `record EmptyResponse`。
- **操作类**：`Operations/<资源 PascalCase>/<方法名去 Async>Operation.cs`，命名空间 `<项目名>.Operations.<资源 PascalCase>`，`[Operation("<资源>.<动词>", Permission = …, Policy = …)]`，主构造函数注入原服务（实现了 `I<类名>` 接口时注入接口，否则注入类），实现 `IOperation<TRequest, TResponse>`，`HandleAsync` 只做委托：`Task<T>` → `async … => await service.M(…).ConfigureAwait(false)`（`T` 的简单名以 `I` + 大写字母开头即接口类型，如 `IReadOnlyList<T>`，没有到 `Result<T>` 的用户定义转换，生成 `=> Result.Success(await service.M(…).ConfigureAwait(false))`），`Task` → 等待后返回 `EmptyResponse.Instance`，同步方法 → `new(Result.Success(…))`；`CancellationToken` 参数传 `context.CancellationToken`。生成的请求记录与操作类同文件；`EmptyResponse` 每项目一个（`Operations/EmptyResponse.cs`，带 `Instance`）。生成文件沿用服务文件的 `using`（4.x 命名空间除外）。
- **不迁移的方法**：非公开、静态、`override`、显式接口实现、`[NonAction]`、`[DynamicApi(false)]` 跳过；泛型方法、`ref` / `out` / `in` 参数、参数或返回类型为流 / 文件 / ASP.NET 类型（`IActionResult`、`FileResult`、`Stream`、`IFormFile`、`byte[]` …）或推出的操作 ID 不合文法的留标记跳过。
- **授权**：方法上的 `[PermissionAuthorize(<表达式>)]` 优先，否则类或基类上的；第一个参数表达式原样作为 `Permission`，多个权限特性或多个参数只取第一个并留标记；无权限但自己、类或基类有 `[Authorize]` → `Policy = "authenticated"`；方法 `[AllowAnonymous]`（或类 `[AllowAnonymous]` 且方法没有自己的授权特性）→ 都不设。
- **序列化**：每个项目生成 `Operations/<项目末段>OperationsJsonContext.cs`（`internal sealed partial class … : JsonSerializerContext`，camelCase、不区分大小写、允许从字符串读数字），为每个请求与响应类型加 `[JsonSerializable]`：工具生成的类型（请求记录、`EmptyResponse`）写全限定名 `typeof(<项目名>.Operations.<资源>.<记录>)`，不给上下文加资源子命名空间的 `using`（不同资源各自生成的同名记录 `DeleteRequest` / `GetDetailRequest` 用简单名会歧义或漏登记）；简单名重复的类型再加 `TypeInfoPropertyName = "<资源 PascalCase><类型名>"`（源生成上下文按简单名推导的属性名会撞车，`Kernel.Generators` 取到的会是另一个命名空间的同名类型），如 `[JsonSerializable(typeof(Shop.Operations.Order.DeleteRequest), TypeInfoPropertyName = "OrderDeleteRequest")]`；来自服务文件的 DTO 类型沿用服务文件的 `using`；可空值类型按 `typeof(int?)` 保留问号、可空引用类型去掉问号；文件第一行留标记提醒在特性的 `Configure` 里 `context.AddGeneratedOperations()`。
- **登记**：原服务类按作用域进 V4-03 的 `<项目末段>V4Services.cs`（实现了 `I<类名>` 时注册到接口）；项目文件加 `<PackageReference Include="XiHan.Framework.Kernel.Generators" PrivateAssets="all" />`。
- 原服务类保留，只删除 `[DynamicApi]`、`[Authorize]`、`[AllowAnonymous]`、`[PermissionAuthorize]`、`[Http*]`、`[Route]`、`[NonAction]` 特性（含标了 `[DynamicApi]` 的抽象基类）；`ApplicationServiceBase` 基类去掉，用到 `Logger` / `ServiceProvider` / `LazyServiceProvider` 的语句留标记（改为构造函数注入）。
- `[DynamicApi]` / `[Authorize]` 是否经基类继承由第一遍扫描的类目录判定（只看同一次迁移范围内的源码）。

### V4-07 `ICurrentUser` / `ICurrentTenant`

不改 255 处调用点。每个用到 `ICurrentUser` / `ICurrentTenant` / `ICurrentPrincipalAccessor` 的项目在自己的项目引用闭包里找同样用到它们、且不再引用其他使用项目的那个（最底层；没有就是自己）作为提供者，在提供者项目生成 `Security/ICurrentUser.cs`、`CurrentUser.cs`、`ICurrentTenant.cs`、`CurrentTenant.cs`、`ICurrentPrincipalAccessor.cs`、`CurrentPrincipalAccessor.cs`、`PrincipalAmbient.cs`、`PrincipalConversion.cs`（命名空间 `<提供者项目>.Security`，已存在不覆盖），使用文件补 `using <提供者项目>.Security;`（4.x 的 `using XiHan.Framework.Security.Users` / `.Claims` 由 V4-10 删除）。接口成员与 4.x 同名，`TenantId` / `Id` 按 V4-02 改成 `string?`；`UserId` 仍是 `long?`（4.x 契约如此，应用按数字主键使用），另加 `string? Subject` 暴露 5.0 主体 ID 原文；`CurrentUser` 读 `IInvocationAccessor.Current` 的 `SecurityContext`（主体 ID 作 `Subject`，`UserId` 用 `long.TryParse(Subject, NumberStyles.None, CultureInfo.InvariantCulture)` 解析，解析不出为空；`Name` / `SurName` / `Email` 按标准 `ClaimTypes`，`phone_number` / `email_verified` / `tenantid` 等沿用 4.x 默认声明名，`TenantId` 先取租户上下文再取声明；4.x 用 `JwtSecurityTokenHandler` 签发令牌，出站把 `ClaimTypes.Role` / `ClaimTypes.NameIdentifier` / `ClaimTypes.Name` 映射成短名 `role` / `nameid` / `unique_name`，而 5.0 的 `JwtAuthenticationHandler` 关闭了入站映射，所以 `Roles` 合并 `ClaimTypes.Role` 与 `role` 两种声明、`IsInRole` 两种都认、`UserName` 先取 `ClaimTypes.Name` 再取 `unique_name`）；`CurrentTenant` 默认读调用携带的租户上下文，`Change(id, name)` 用 `AsyncLocal` 覆盖栈实现（压栈、释放弹栈，`Id` / `Name` 先看覆盖再看调用携带的租户，空白 `id` 表示切到平台），调用点原样保留、不留标记。`ICurrentPrincipalAccessor` 与 4.x 同名成员（`ClaimsPrincipal Principal`、`IDisposable Change(ClaimsPrincipal)`）：`PrincipalAmbient` 是执行流上的主体覆盖（静态 `AsyncLocal<ClaimsPrincipal?>`，`Override(principal)` 压栈、释放弹栈），`CurrentPrincipalAccessor.Principal` 有覆盖读覆盖、否则把调用携带的 5.0 `Principal` 转成 `ClaimsPrincipal`，`Change` 登记覆盖（后台任务以指定用户身份执行）；`PrincipalConversion` 在 5.0 `Principal`（键值声明）与 `ClaimsPrincipal` 之间互转（声明按原名复制，认证类型取认证方案；反向时标识依次取 `ClaimTypes.NameIdentifier`、`sub`、`nameid`，取不到视为匿名，没有认证类型时方案名为 `ambient`）；生成的 `CurrentUser` 优先读 `PrincipalAmbient.Current`（经 `PrincipalConversion` 转回 5.0 主体），没有覆盖才读调用携带的主体。三者按作用域进 V4-03 的 `<项目末段>V4Services.cs`。
